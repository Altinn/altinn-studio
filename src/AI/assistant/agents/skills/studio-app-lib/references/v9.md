## Interfaces that have other names in v8

| Job | Interface | Namespace |
| --- | --- | --- |
| Run code when a task starts | `IOnTaskStartingHandler` | `Altinn.App.Core.Features.Process` |
| Run code when a task ends, before the process moves on | `IOnTaskEndingHandler` | `Altinn.App.Core.Features.Process` |
| Run code when a task is abandoned, such as on reject | `IOnTaskAbandoningHandler` | `Altinn.App.Core.Features.Process` |
| Run code after the process has ended and is saved | `IOnProcessEndedHandler` | `Altinn.App.Core.Features.Process` |
| Work the app does on its own in the process | `IServiceTask` | `Altinn.App.Core.Features.Process` |
| File analyzer: read facts from an uploaded file | `IFileAnalyzer` | `Altinn.App.Core.Features.FileAnalysis` |

The template's `App/App.csproj` has a global `<Using>` for `Altinn.App.Core.Features`, not for its sub-namespaces.

## Process hooks

The workflow engine runs each hook as a step of its own, and retries it when it fails.
[Definere egne prosess-hooks](https://docs.altinn.studio/nb/altinn-studio/v9/develop-a-service/reference/configuration/process/pre-post-hooks/)
shows how to write a hook, change data through it and report the result. The page leaves out the first and last of
these rules:

- `ShouldRunForTask(taskId)` picks the tasks. The app calls it more than once, so the answer must depend on the task
  ID alone.
- At most one hook of each kind may run for a task, and an app registers at most one `IOnProcessEndedHandler`. With
  more, the app does not start. Combine them into one class.
- Write the hook so a second run does no harm. Use `context.StepId` as the idempotency key for a call to another
  system.

## Service tasks

An `IServiceTask` composes its work as a pipeline in `DefineExecute`. A task that does one thing has only the
concluding step:

```csharp
public class MyServiceTask : IServiceTask
{
    public string Type => "myServiceTask";

    public ServiceTaskPipeline DefineExecute(PipelineBuilder pipeline) => pipeline.Finally(Execute);

    private async Task<ServiceTaskResult> Execute(StageContext context)
    {
        // Read and change data through context.InstanceDataMutator
        return ServiceTaskResult.Success();
    }
}
```

- Every step must survive a second run, like a hook.
- Work with several steps, such as sending something and waiting for the answer, gets a `Stage` per step before
  the conclusion. [Service task pipelines](https://github.com/Altinn/altinn-studio/blob/main/src/App/backend/docs/service-task-pipelines.md)
  in the app library source is the guide until the docs catch up.
- A user needs `write` to retry a service task. It needs no action named after its `Type`.
- `IProcessTask` composes the work at start, end and abandon the same way, in `DefineStart`, `DefineEnd` and
  `DefineAbandon`. The methods `Start`, `End` and `Abandon` are gone.

## Removed in v9

| v8 | Use instead |
| --- | --- |
| `IProcessTaskStart`, `IProcessTaskEnd`, `IProcessTaskAbandon` | The handlers above. Each needs `ShouldRunForTask`. |
| `IProcessEnd` | `IOnProcessEndedHandler` |
| `IPipelineServiceTask` (in earlier 9.0 previews) | `IServiceTask` |
| `IPdfFormatter` | `excludeFromPdf` in the task's layout settings, or a PDF service task with a layout of its own |
| `IEventHandler` | Nothing. The app no longer receives Altinn Events. The `studio-integrations` skill has the options. |
| `IPageOrder` | An expression that hides the page (the `studio-layouts` skill) |
| `IFileAnalyser` and its `Analyse` method | `IFileAnalyzer` and `Analyze` |

`studioctl app upgrade v9` renames what it can and lists the rest. It does not port process hooks.

## Other changes from v8

- From 9.0.0-preview.8, methods no longer end in `Async`: `GetAppOptions`, `GetInstanceAppOptions`, `GetDataList`,
  `GetInstanceDataList`, `GetExternalApiData`, `ReadOptionsFromFile` and `IProcessExclusiveGateway.Filter`. Apps on
  an earlier v9 preview still use the names with `Async`.
- `IProcessExclusiveGateway.Filter` has one overload, which gets an `IInstanceDataAccessor`. Read data through it. A
  direct `IDataClient` call in a gateway acts as the user, not as the app.
- The classes behind the library's services are internal. Inject the interface, such as `IAppMetadata` or
  `IDataClient`, and never construct or derive from the class.
- The eFormidling and Fiks Arkiv interfaces changed too. The `studio-integrations` skill covers them.

## Source and docs

- The v9 source is `src/App/backend` in [Altinn/altinn-studio](https://github.com/Altinn/altinn-studio/tree/main/src/App/backend).
  Releases are tagged `app/v<version>`, such as `app/v9.0.0-preview.9`.
- [Definere egne prosess-hooks](https://docs.altinn.studio/nb/altinn-studio/v9/develop-a-service/reference/configuration/process/pre-post-hooks/):
  the four hooks, retries, and how to change a hook's timeout and retry strategy.
- [Definere egne gateways](https://docs.altinn.studio/nb/altinn-studio/v9/develop-a-service/reference/configuration/process/exclusive-gateways/):
  the gateway in `process.bpmn` and its registration. The page names the method `FilterAsync`. From 9.0.0-preview.8
  it is `Filter`.
- [Lage egne regler for å starte appen](https://docs.altinn.studio/nb/altinn-studio/v9/develop-a-service/reference/configuration/instantiation-validation/):
  `IInstantiationValidator`.
- Do not follow the code on the pages [Lage en egendefinert systemoppgave](https://docs.altinn.studio/nb/altinn-studio/v9/develop-a-service/process/service-tasks/custom/)
  and [Systemoppgaver med flere steg](https://docs.altinn.studio/nb/altinn-studio/v9/develop-a-service/process/service-tasks/flere-steg/).
  They show `Execute(ServiceTaskContext)`, `StepOptions` and `IPipelineServiceTask`, which v9 no longer has.
