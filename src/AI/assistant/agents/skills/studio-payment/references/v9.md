# Payment in v9 apps

- `IOrderDetailsCalculator` has this method:

  ```csharp
  Task<OrderDetails> CalculateOrderDetails(
      Instance instance,
      string? language,
      CancellationToken cancellationToken = default
  );
  ```

- The app refuses to start when a payment task has no `paymentConfig` or lacks one of its IDs, and, in Development,
  when the payment data type is missing or not app-owned. Nothing at startup checks `IOrderDetailsCalculator` or
  `NetsPaymentSettings`. A mistake there fails when a payment starts.
- The build checks most of the setup against these rules:
  - No data type has a `taskId`, which v9 no longer reads. Use `taskIds`.
  - Both data types the task names exist in `applicationmetadata.json`, and the task names both.
  - The receipt data type allows `application/pdf`.
  - The payment data type is app-owned.
- The payment task's pages are the UI folder `App/ui/<payment task id>/`. Its `Settings.json` needs a
  `defaultDataType` and lists the payment page in `pages.order`. It can hold `pages.pdfLayoutName`. The
  `studio-layouts` skill covers UI folders.
- [Setting up the payment pages](https://docs.altinn.studio/nb/altinn-studio/v9/develop-a-service/process/payment/backend-manual/configure-layouts/)
  shows how `PaymentDetails` refetches the order when an expression in its `refetchDependencies` changes value.
- Studio provisions the app's Maskinporten client with the service owner scopes that let the process move on when
  Nets reports the payment.
- Grant the service owner `read` and `write` in a rule that is not scoped to a task, or the build warns that it
  cannot verify the grant. Its `confirm` on the payment task can be in a rule of its own.
