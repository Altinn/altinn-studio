# Payment in v9 apps

- `IOrderDetailsCalculator` has this method:

  ```csharp
  Task<OrderDetails> CalculateOrderDetails(
      Instance instance,
      string? language,
      CancellationToken cancellationToken = default
  );
  ```

  Write all three parameters. The example on the v9 docs page has two, which does not compile in a v9 app.
- The app refuses to start when a payment task has no `paymentConfig` or lacks one of its IDs, and, in Development,
  when the payment data type is missing or not app-owned. Nothing at startup checks `IOrderDetailsCalculator` or
  `NetsPaymentSettings`. A mistake there fails when a payment starts.
- `dotnet build` reports most mismatches before you start the app:
  - ALTINNAPP1013: the task names a data type that `applicationmetadata.json` does not declare
  - ALTINNAPP1015: the receipt data type cannot hold a PDF
  - ALTINNAPP1016: the payment data type is not app-owned
  - ALTINNAPP1020: one of the two IDs is missing
- The payment task's pages are the UI folder `App/ui/<payment task id>/`. Its `Settings.json` needs a
  `defaultDataType` and lists the payment page in `pages.order`. It can hold `pages.pdfLayoutName`. The
  `studio-layouts` skill covers UI folders.
- `PaymentDetails` refetches the order when a value in `refetchDependencies` changes. Each value is an expression,
  and the key is any name. The app does not receive the values.

  ```json
  "refetchDependencies": {
    "inventory": ["dataModel", "GoodsAndServicesProperties.Inventory.InventoryProperties"]
  }
  ```

- Studio provisions the app's Maskinporten client with the service owner scopes that let the process move on when
  Nets reports the payment.
- Grant the service owner `read` and `write` in a rule that is not scoped to a task, or the build warns with
  ALTINNAPP0801. Its `confirm` on the payment task can be in a rule of its own.
