# The process in a v9 app

A v9 app checks `process.bpmn` twice: when it builds, and when it starts. The next two sections say what each check
needs. A build error or warning names the element and says what to change.

## The app refuses to start

At startup the app collects every problem it finds in the process and stops with "Process configuration is not
valid". It refuses:

- a task with a missing or blank `<altinn:taskType>`
- a type that no built-in or registered task answers to, matched exactly, including case. `fiksArkiv` needs
  `services.AddFiksArkiv()`.
- the wrong element for the type. Every service task type, built in or your own, must be a `<bpmn:serviceTask>`, and
  every other type a `<bpmn:task>`. The frontend chooses how to show a task from its element.
- a task setting that is missing or invalid in the environment the app runs in, such as a signing task without
  `signatureDataType`, a PDF task with nothing to render, or an eFormidling task without `process`
- a gateway whose `default` flow has a condition
- a gateway with more than one flow, where a flow other than the default has no condition. A gateway with no
  conditions at all that your `IProcessExclusiveGateway` decides is the exception.

The app logs a warning for a registered service task type that no task uses.

The Fiks Arkiv package checks its own tasks at startup and stops the app with a `FiksArkivConfigurationException`
when a Fiks Arkiv task is not followed only by exclusive gateways with at least two outgoing flows each. When the
archive refuses the record, the task moves on with its error action, `reject` by default, so the gateway needs a flow
for `["equals", ["gatewayAction"], "reject"]`.

## The build checks the process

Besides the flow rules in `SKILL.md` and the startup checks above, the build checks these rules:

- Every flow leads to a task, a gateway or an end event of the process. Every element except an end event has an
  outgoing flow.
- A gateway's `default` names one of the flows in its `<bpmn:outgoing>`.
- Every data type the process names exists in `applicationmetadata.json`, written the same way. That includes the
  data types of signing, payment and PDF tasks, and a gateway's `connectedDataTypeId`.
- Each data type a task stores in can hold what it stores, such as `application/pdf` for a PDF. Signing and payment
  data types are app-owned. The `studio-signing` and `studio-payment` skills cover their data types.
- Every task ID in a data type's `taskIds` names a task.
- A PDF task has a `ref-data-as-pdf` data type, and has something to render: tasks in `<altinn:autoPdfTaskIds>` whose
  pages the PDF can show, or a `pdfLayoutName` in its folder's `Settings.json` that names a page in the folder.
- A `subformPdf` task's `subformUiFolder` names a subform folder that the app can render.
- An `env` attribute on a task setting is written `env`, in lowercase and without a prefix, and names an
  environment the app recognizes, such as `development`. The app applies an entry with any other `env` in no
  environment, or in every one.

The build checks most flow rules only for what an instance can reach from the start event, so it passes a task you
have placed but not connected yet. It checks every element for a duplicate id, a gateway that mixes flows with and
without a condition, and a condition on a gateway's default.

## Gateways: `default` is a fallback

v9 treats `default` as BPMN does:

- The app evaluates the condition of every listed flow except the default. A flow without a condition counts as true.
- Exactly one true flow: the app takes it. More than one: the app fails.
- No true flow: the app takes the default, or fails when the gateway has none.
- The app never evaluates the default's own condition, so the default must have none.

The form in `SKILL.md`, with a condition on every flow and no `default`, works. So does a default without a
condition beside flows that all have one:

```xml
<bpmn:exclusiveGateway id="Gateway_1" default="Flow_other">
  <bpmn:incoming>Flow_t1_g1</bpmn:incoming>
  <bpmn:outgoing>Flow_back</bpmn:outgoing>
  <bpmn:outgoing>Flow_other</bpmn:outgoing>
</bpmn:exclusiveGateway>
<bpmn:sequenceFlow id="Flow_back" sourceRef="Gateway_1" targetRef="Task_1">
  <bpmn:conditionExpression xsi:type="bpmn:tFormalExpression">["equals", ["gatewayAction"], "reject"]</bpmn:conditionExpression>
</bpmn:sequenceFlow>
<bpmn:sequenceFlow id="Flow_other" sourceRef="Gateway_1" targetRef="Task_2" />
```

When a condition reads the data model and the gateway has no `connectedDataTypeId`, the app uses `defaultDataType`
in `ui/<taskId>/Settings.json` of the task being left.

The v9 docs pages on gateways do not describe `default`, and they still call the gateway method `FilterAsync`. From
9.0.0-preview.8 it is `Filter`.

## UI folders

- There is no `layout-sets.json`. A task's pages are in `App/ui/<taskId>/`, and its `Settings.json` holds
  `pages.order` and `defaultDataType`.
- Data, signing and payment tasks need the folder with a `defaultDataType` that `applicationmetadata.json` declares.
  Studio reports a task without one.
- When you rename a task, rename its folder.
- A PDF task needs a folder only for a PDF of its own pages: `pages.pdfLayoutName` and `"order": []`.
- A service task's folder can list pages in `pages.order` for users to see while the task runs. See
  [Hva brukeren ser](https://docs.altinn.studio/nb/altinn-studio/v9/develop-a-service/process/service-tasks/visning/).
- A `subformPdf` task needs no folder. Its `subformUiFolder` names the subform's own folder, which has
  `"type": "subform"`.

The `studio-layouts` skill covers the pages.

## The workflow engine runs the transitions

- `PUT .../process/next` authorizes the user, runs the action's handler, validates, and works out the next task.
  Then the workflow engine runs the task end, the commit, the next task's start and any service tasks, each as a step
  that it retries when it fails. The steps and the gateways act as the service owner.
- The process stops on a service task while it runs. eFormidling and Fiks Arkiv wait there for their answer, so a
  `feedback` task after them is usually a v8 leftover.
- A service task finishes with `ServiceTaskResult.Success(action)`. That action is what `["gatewayAction"]` sees in
  the gateway after the task.
- When a step fails for good, `process/next` answers 409 with `resumeRequired` for every action, `reject` included.
  `POST .../process/resume` runs the failed step again. The frontend offers this as a retry button, which needs
  `write` on the service task's id. There is no way back from a failed service task, so a reject branch after a
  service task only helps when the task itself finishes with `reject`.
- `PUT .../process/completeProcess` is gone. Leave a feedback task with `PUT .../process/next`.
- A data type belongs to the tasks in its `taskIds`. The app and Storage refuse to create, change or delete its data
  in any other task, also from task hooks, service tasks and the app's own `IDataClient` calls. Add every task that
  writes the data to `taskIds`. A task-start hook runs in the task being started. A data type without `taskIds`
  belongs to no task, so the app neither creates nor validates it in any task.
- After a change in Studio's process editor, check that no data type in `applicationmetadata.json` has a `taskId`,
  and that each `taskIds` names the right tasks.

## Policy

- A user needs `write` on a service task's own id to retry it, for built-in service tasks and your own alike.
- Storage always lets the service owner commit a transition, so the service owner needs no task-specific action
  such as `reject`. The exception is `confirm` on a payment task: when the payment provider reports a payment, the
  app calls its own `process/next` with `confirm` as the service owner, and the policy must permit that.
- The build fails when the policy does not grant the service owner the other actions the app takes as the service
  owner. Adding an eFormidling or Fiks Arkiv task adds `complete` to them.

The `studio-policy` skill writes the rules. The v9 docs page on writing your own service task still says the service
owner needs an action named after the task type, and `reject` for a reject flow. Neither is needed. The page on what
users see says a user who retries your own service task needs that action too. The user needs only `write`.

## Legacy settings are build errors

v9 has no PDF or eFormidling that runs beside the process. These v8 settings stop the build:

- `"enablePdfCreation": true` on a data type. Add a PDF service task.
- The `eFormidling` block in `applicationmetadata.json`. Add an eFormidling service task.
- `subformComponentId` or `subformDataTypeId` on a `subformPdf` task. Use `subformUiFolder`.
- `taskId` on a data type. Replace it with `taskIds`, the list of the data type's tasks. Next to `taskIds`, a
  `taskId` only gives a warning, since the app ignores it. Remove it too.

## What the upgrade to v9 changes in the process

[The upgrade guide](https://docs.altinn.studio/nb/altinn-studio/v9/new-in-v9/upgrade/) says how
`studioctl app upgrade v9` turns layout sets into UI folders, and legacy PDF, eFormidling and `subformPdf` settings
into service tasks. It leaves out these changes:

- The upgrade inserts a PDF task only for a data type with `"enablePdfCreation": true`. A missing
  `enablePdfCreation`, which v8 counted as `true`, gets no PDF task. Neither does a task with no outgoing flow or
  several, and the upgrade warns about it.
- It sets `connectedDataTypeId` on the gateways after each PDF task it inserts.
- It adds the service owner's grants, and the users' `read` and `write` on the service tasks it inserts.

It does not change these, and the app does not start until you do:

- a service task type on a `<bpmn:task>` element, such as eFormidling or Fiks Arkiv tasks that v8 ran that way
- a condition on a gateway's default flow, and flows without a condition beside flows with one
- a Fiks Arkiv task without a gateway after it

The upgrade guide does not list these yet.
