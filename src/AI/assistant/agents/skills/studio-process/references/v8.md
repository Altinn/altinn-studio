# The process in a v8 app

A v8 app checks almost nothing in `process.bpmn` before an instance reaches a task. An unknown task type, a missing
setting or a gateway with no valid flow fails only then. Run an instance through every branch before you finish.

## Gateways: `default` is not a fallback

A v8 gateway evaluates its flows like this:

- When any listed flow has a condition, the app evaluates every listed flow, the default included. A flow without a
  condition counts as true. Exactly one flow must be true, or the app fails with "returned N flows. Expected 1". The
  `default` attribute changes nothing.
- When no flow has a condition and no `IProcessExclusiveGateway` has the gateway's id, the app follows every listed
  flow. If `default` names one of them, it follows only that one.

So write every outgoing flow with a condition, as `SKILL.md` describes. Some v8 apps put `default` on a flow that
also has a condition. That works in v8 but stops the app from starting in v9, so remove the `default` attribute when
you change such a gateway.

The v8 docs page on flow control says more than one valid flow is allowed when one of them is the default. The code
does not do that. The page's first example also lists `Flow_g1_t2` as `<bpmn:incoming>` on the gateway, so the app
would never take that flow.

When a condition reads the data model and the gateway has no `connectedDataTypeId`, the app uses the `dataType` of
the layout set that lists the task being left.

## UI: layout sets

- `App/ui/layout-sets.json` lists the layout sets: `{ "id": "form", "dataType": "model", "tasks": ["Task_1"] }`.
  The pages of a set are in `App/ui/<setId>/`.
- A data, signing or payment task needs a set that lists its id in `tasks`. One set can serve several tasks.
- When you rename a task, rename it in `tasks` too. Studio names the sets it creates after the task id.
- A subform's set lists no tasks.

The `studio-layouts` skill covers the pages.

## Service tasks run inside the request

- Service tasks need `Altinn.App.Api` 8.9.0 or later. Upgrade an older app before you add one.
- When `process/next` moves the process into a service task, the app runs the task in the same request, as the user,
  and moves on. It repeats this for each service task in a row.
- So the user needs, on the service task's own id, `write` for a built-in service task and an action named after the
  type for your own `IServiceTask`. A rule scoped to the data task does not cover `PdfTask_Task_1`. The
  `studio-policy` skill covers the rules.
- v8 also runs a service task type declared as `<bpmn:task>`. The frontend shows its service task view only for
  `<bpmn:serviceTask>`, so use that element. It is also what v9 requires.
- A service task needs no `<altinn:actions>`, except `reject` for going back, as below.

## Recovery with `reject`

- When a service task fails, the instance stays on it. The frontend shows a page with a retry button, which calls
  `process/next` again. The button needs `write`, and for your own service task the call also needs the action
  named after its type.
- The page also shows a back button when the service task lists `reject` and the policy grants it. `reject` skips
  the service task and moves on with `["gatewayAction"]` = `reject`.
- Route it with a gateway right after the service task: `["equals", ["gatewayAction"], "reject"]` back to the data
  task, and `["notEquals", ["gatewayAction"], "reject"]` onwards.
- Your own service task can also give up and move on with an action, such as
  `ServiceTaskResult.FailedContinueProcessNext("reject")`.

## Legacy PDF and eFormidling still run

At the end of every task, v8 also runs the PDF and eFormidling code from before service tasks existed. Both run
beside the service tasks:

- Legacy PDF: the app makes a PDF at the end of a task for a data type with that `taskId`, an `appLogic.classRef`
  and `enablePdfCreation` that is `true` or missing. A missing `enablePdfCreation` counts as `true`. When you add a
  PDF service task, set `"enablePdfCreation": false` on the data model types of the tasks it covers, or the app
  makes two PDFs. The v8 template does this.
- Legacy eFormidling: the app sends at the end of the task in `eFormidling.sendAfterTaskId` in
  `applicationmetadata.json` when `AppSettings.EnableEFormidling` is `true`. Do not combine it with an eFormidling
  service task.

## Settings only v8 has

- A `subformPdf` task names `subformComponentId` and `subformDataTypeId`. Both are required.
- A PDF task with its own pages has a layout set that lists the PDF task, with `pages.pdfLayoutName` in its
  `Settings.json`.

## The v7 form

Some v8 apps still have the v7 process form: `xmlns:altinn="http://altinn.no"` and an attribute such as
`altinn:tasktype="data"` on the task. v8 does not read it. The task has no type, and an instance fails when it enters
the task. Rewrite each task with `<altinn:taskExtension><altinn:taskType>` in `http://altinn.no/process`, and remove
the obsolete `altinn:flowtype` attribute from sequence flows.
