# Validation in a v9 app

## The backend checks are on by default

In v9, `RequiredValidation`, `ExpressionValidation` and `RemoveHiddenData` under `AppSettings` in
`App/appsettings.json` are `true` by default, so do not add them. Setting `RequiredValidation` or
`ExpressionValidation` to `false` turns that check off on `process/next`, so the rule then runs only in the browser.

Keep a `false` that the app already has, unless the user asks to change it. Removing `RemoveHiddenData: false` makes
the app delete the data of hidden fields when the task ends, data it kept until then.

The [expression validation page](https://docs.altinn.studio/nb/altinn-studio/v9/develop-a-service/data/validation/expression-validation/)
says the backend runs the rules only after you set `ExpressionValidation` to `true`. That is wrong for v9.

The backend checks required fields against the pages in the task's UI folder, `App/ui/<taskId>/`.

## Hidden fields and the data model check

With `RemoveHiddenData` on, as by default, the backend skips the C# attributes on fields that hidden components bind,
and the app deletes their data when the task ends. With it off, a value the user entered before the field was hidden
can stop the submit.

## What the user sees

- The error summary shows only after the user has tried to submit, or to change page where the app checks the page.
  When the user fixes the errors, it goes away until the next attempt.
- The validation type `Invalid` covers input the app cannot store in the data model, such as text in a number field.
  `AllExceptRequired` includes it. The user cannot leave a subform while such input remains.
- When a C# issue names a `CustomTextKey` that the text resources lack, the frontend shows `Description` instead,
  then `Code`.

## Files

The validation file uses the schema
`https://altinn.studio/designer/app-dist/<version>/schemas/json/validation/validation.schema.v1.json`. Use the
version the app's layout files use.

## Docs

- [Validering med uttrykk](https://docs.altinn.studio/nb/altinn-studio/v9/develop-a-service/data/validation/expression-validation/):
  the file format, with `definitions` and `ref`. The example writes `lowercase`, which must be `lowerCase`.
- [Validering](https://docs.altinn.studio/nb/altinn-studio/v9/develop-a-service/data/validation/): which mechanism to
  choose, the validation types for `showValidations`, and in "Validering på serveren" a table of the built-in checks
  on the backend and the setting for each.
- [Påkrevde felt](https://docs.altinn.studio/nb/altinn-studio/v9/develop-a-service/data/validation/required/): how the
  app builds the required message from `shortName` and `title`.
- [Begrensninger i datamodellen](https://docs.altinn.studio/nb/altinn-studio/v9/develop-a-service/data/validation/data-model/): the
  built-in messages for each schema keyword, and `errorMessage`.
- [Validering i C#](https://docs.altinn.studio/nb/altinn-studio/v9/develop-a-service/data/validation/csharp/): the
  interfaces, severity, and messages in several languages.
- [Navigasjon](https://docs.altinn.studio/nb/altinn-studio/v9/develop-a-service/look-and-feel/sider/navigasjon/): in
  "Angi validering ved sidebytte", where `validationOnNavigation` and the keys on the navigation components go, and
  which one wins.
