## In v8 apps: the upgrade is held back

The upgrade changed nothing, because layouts or legacy rules need manual work. In turn 2, fix the blockers on v8, and then run the upgrade again in the same turn.

1. Run `upgrade_app_to_v9`, and read the TODOs. The rollback removed the markers and the generated files that the TODOs name. Read the rules in `App/ui/<layout set>/RuleConfiguration.json` and `RuleHandler.js`.
2. For each conditional rendering rule (`conditionalRendering`) in a TODO:
   - Write a `hidden` expression on each target component, with the same condition as the JavaScript function.
   - Remove the rule from `conditionalRendering`. If the rule stays, the upgrade adds a placeholder again.
3. For each data processing rule (`ruleConnection`) in a TODO:
   - Write a class in `App/logic/` that implements `IDataWriteProcessor` and does what the JavaScript function does.
   - Register it in `App/Program.cs`: `services.AddTransient<IDataWriteProcessor, X>();`.
   - Remove the rule from `ruleConnection`.
4. Fix the conflicting bindings and the layouts that do not parse.
5. Run `verify_changes`. It builds the C#. If the app has an old v8 version of `Altinn.App.Core` without `IDataWriteProcessor`, the build fails. Then stop, and tell the user that the app needs a newer v8 version first.
6. Run `upgrade_app_to_v9` again. Do not commit first. Your verified changes stay in the working tree, and the upgrade runs on top of them.
   - **Completed**: the app is on v9, and the upgrade and your fixes are staged together. Fix the TODOs that remain and that you offered, as for a v9 app. Then verify and commit.
   - **Still held back**: your fixes stay, so you can fix the next blockers and run the upgrade again. If you cannot fix them, stop. `commit_session_branch` refuses the fixes, and the end of the turn discards them, so the app stays as it was before the turn. Tell the user what still blocks the upgrade.
