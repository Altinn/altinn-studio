# Workflow Engine Integration Layer

App-lib integration with the async Workflow Engine service. The engine runs as a separate service; this code handles **submitting workflows**, **waiting for them to settle**, and **receiving callbacks**.

## Architecture

The Workflow Engine service (external, .NET, PostgreSQL-backed) orchestrates process transitions. This integration layer:

1. **Orchestration**: `WorkflowEngineService` (`IWorkflowEngineService`) is the entry point used by the process engine. It builds the enqueue request, submits it, polls the engine until the transition settles, refetches the instance from Storage, and classifies any failure. It also exposes the reject/resume/abandon operations.
2. **Outbound**: `ProcessNextRequestFactory` builds a `WorkflowEnqueueEnvelope` (the `WorkflowEnqueueRequest` body + the metadata that travels via URL path and HTTP headers: namespace, idempotency key, collection key). `WorkflowEngineClient` POSTs it to the engine's enqueue endpoint (`POST {ApiWorkflowEngineEndpoint}/{namespace}/workflows`). Namespace is sent in the URL path; idempotency key and collection key go in HTTP headers (`Idempotency-Key`, `Collection-Key`). Context (`AppWorkflowContext`) carries actor, lock token, org/app, instance identification, and the callback token. `Namespace` = `{org}/{app}` (isolation boundary); the instance guid is the collection key and is also sent as the `processNextInstanceGuid` label (for querying all workflows for an instance).
3. **Inbound**: The engine calls back to `WorkflowEngineCallbackController` (in the **Altinn.App.Api** project, not this folder) for each app command, one at a time, sequentially.
4. **Per-callback lifecycle**: The controller restores the signed state blob into two halves — an `InstanceDataUnitOfWork` and a `WorkflowCallbackStateCarry` (the non-data bookkeeping: the mailboxes a service task's stages have opened, keyed by the stage that opened each) — resolves the `IWorkflowEngineCommand` by key, executes it with both, saves data changes on success, captures the updated (re-signed) state from both, and returns it to the engine. A command that never looks at the carry forwards it unchanged, which is how a mailbox id crosses the steps between the mint step that recorded it and the steps that read it. A **deferral** is deliberately different: it is stateless — nothing is saved, the incoming state is echoed back unchanged (the re-run starts exactly where this attempt did), and a deferring handler that made data changes is rejected with a non-retryable 422. A step that checks-and-waits is not a step that records; work that produces something durable belongs in its own pipeline stage.

```text
App ProcessNext API
  → ProcessEngine calls IWorkflowEngineService.EnqueueAndWaitForProcessNext()
      → ProcessNextRequestFactory.Create()         (builds WorkflowEnqueueEnvelope from ProcessStateChange)
      → WorkflowEngineClient.EnqueueWorkflows()     (HTTP POST → engine, returns WorkflowEnqueueResponse.Accepted)
      → Poll the workflow collection until it settles, then refetch the instance from Storage
      → Classify the outcome into ProcessNextWorkflowResult (instance, WorkflowFailure?, ProcessStateChanged)

Engine (external service)
  → Executes steps sequentially
  → For each app command: POST to /workflow-engine-callbacks/{commandKey} (echoes the signed state blob)

WorkflowEngineCallbackController.ExecuteCommand()   (Altinn.App.Api)
  → Restore + verify workflow callback state from the signed blob (WorkflowCallbackStateService)
  → Resolve IWorkflowEngineCommand by key
  → command.Execute(context)
  → Save data changes on success, capture + re-sign updated state blob, return to engine
  → (Engine uses the returned state blob for the next callback)
  → On success with AutoAdvanceProcess, enqueue a dependent process-next workflow
```

## Key Design Constraints

- **ALL commands MUST be idempotent** - the engine retries failed commands with configurable backoff
- **Commands run in separate HTTP requests** - each callback is independent; state is passed between commands via a signed, opaque JSON blob (see State Passthrough below)
- **Command phases**: task-end/abandon commands → `MutateProcessState` (in-memory state transition) → task-start / process-end commands → `SaveProcessStateToStorage` (persist to Storage, the commit boundary) → `EnqueueSideEffectsWorkflow` (schedules the non-critical side-effect commands as separate `IsHead=false` single-step workflows, one per side effect, when the transition has any) → critical post-commit commands (see Command Sequences)
- **Task-start reads get a clean slate.** `CleanupGeneratedFromTask` runs before the task-start hooks and removes elements generated by previous visits to the entering task (mirroring Storage's cleanup contract, but early enough that `OnTaskStartingHook`/`StartTask` never see stale data). An element referencing the entering task that is visible at task start was created by a retried attempt of the same transition.
- **`generatedFromTask` tagging is safe in any phase, including task start.** Storage's cleanup at `PutInstanceAndEvents` (stale data from previous visits - see altinn-storage#977 / app-lib-dotnet#1750) is timestamp-guarded: it only deletes elements created before the in-flight transition began, so elements created by task-start commands survive the save that completes their own transition. `SigningService` relies on this - signee states are created during task start tagged with the signing task. NOTE: the guard must exist in the Storage backend the app runs against (localtest has it; the altinn-storage PR must be deployed before this app-lib version is released).
- **Callback authentication** (see `Authentication/`): The app mints a JWT at enqueue time (signed with a `WorkflowEngineCallback` app-code, `jti` = instance guid, `secretId` claim identifies the code), carries it opaquely through the engine in `AppWorkflowContext.CallbackToken`, and the engine replays it on every callback in the `Authorization: Bearer` header. The callback controller authenticates with the `WorkflowEngineCallback` scheme (`WorkflowEngineCallbackAuthenticationHandler` in Altinn.App.Api); a selector policy scheme routes callback requests to it and all other requests to the default scheme, so the bearer token does not collide with platform auth. Validation checks signature, lifetime, and that `jti` matches the route instance. Data operations use `StorageAuthenticationMethod.ServiceOwner()`.
- **A workflow cannot outlive the app code that signed it, and nothing checks that it will not.** `WorkflowCallbackTokenGenerator` mints the callback token **once**, at the workflow's enqueue, with `Expires` set to the _signing code's_ `ExpiresAt` rather than to a lifetime of its own; the state blob that workflow carries is signed with the same code, and `WorkflowStateSigner` rejects it once the code expires. Neither is ever refreshed while it waits. Any workflow still waiting when its code expires therefore fails on the next callback: authentication runs first, so it is a **401**, which the engine host classifies as a client error (`AppCommand` treats every 4xx except 408/418/429 as a critical error) — so the step and its workflow go terminally `Failed` on the **first** attempt, with no retries and no backoff, and a resume replays the same stored token and fails the same way. This is a property of **long-running work in general, not of mailboxes**: an ordinary step deferring against the engine's `MaxStepWaitBudget` (14 days) and a mailbox receiver parked on `MaxMailboxTimeout` (21 days) fail identically, and neither is guarded. The exposure is bounded operationally rather than in code — the engine derives both maxima against the operator's app-code rotation policy, which leaves ≥114 days of remaining validity at enqueue against a worst case of 110 days (see the `MaxMailboxTimeout` xmldoc in `WorkflowEngine.Models/EngineSettings.cs` and `CallbackTokenLifetimeInvariantTests`).
- **State blob is signed independently of the token** (see `WorkflowStateSigner`): a leaked callback token cannot be combined with a forged/tampered state blob, because the blob carries a detached HMAC-SHA256 signature bound to a secret only the app holds. Signature/secret failures map to a non-retryable 422.

## Command Sequences

Defined in `WorkflowCommandSet.cs`; `ProcessNextRequestFactory.AssembleCommandSequence` assembles the sequences:

1. Task-end/abandon commands (from `process_EndTask`/`process_AbandonTask` events)
2. `MutateProcessState` (inserted by the factory if there are task-end/abandon commands)
3. Task-start and process-end commands (from `process_StartTask`/`process_EndEvent` events)
4. `SaveProcessStateToStorage` (always inserted by the factory)
5. `EnqueueSideEffectsWorkflow` (inserted by the factory when the transition has side-effect
   commands) — enqueues the **side-effects workflow**
6. Critical post-commit commands (`CriticalPostCommitCommands`) — must complete before the
   transition settles

All of the above form the **Main workflow** — the only workflow in the enqueue batch. The
non-critical side-effect commands (`SideEffectCommands`) travel inside step 5's payload as a
pre-assembled enqueue request; when that step executes — immediately after the commit — it submits
them to the engine as separate **side-effects workflows, one single-step workflow per side effect**,
in one atomic batch. Each sibling is an independent root (`DependsOn = null`,
`DependsOnHeads = false`), invisible to the collection heads frontier (`IsHead = false`), carrying
the commit-time state blob as its own state (see State Passthrough), `links`-related to the Main
workflow, with an OperationId prefixed `Process next side-effects:` and suffixed with its command
key (e.g. `Process next side-effects: Task_1 -> Task_2 · MovedToAltinnEvent`). The batch enqueue is
idempotent per Main workflow (one idempotency key, `{mainWorkflowId}:side-effects`, covering the
whole batch — the engine's batch enqueue is atomic), so step retries dedup. Because the step runs
inside Main before it settles, the side effects exist **if and only if** the transition committed —
a pre-commit failure schedules nothing, and a committed transition's side effects run independently
of whatever happens to Main afterwards (post-commit failure, reject/abandon). The ProcessNext wait
and the next transition key off Main only: a slow or failing event registration can never gate the
API response or wedge the instance's process pipeline, and the side effects start at the commit
rather than after e.g. a service task. One workflow per effect means the effects also fail
independently of _each other_: a dead-lettered event registration cannot starve the notification
behind it, each effect gets its own retry pacing and redrive, and a failed workflow is named for
the one effect it carries. When there are no side-effect commands, a single workflow without the
enqueue step is emitted — identical to the pre-split behavior.

**Ordering is not guaranteed between side effects at all** — neither across transitions nor between
effects of the same transition (each rides its own workflow): a retrying `movedTo.Task_2`
registration can land after `movedTo.Task_3` (or after `completed`). This matches the platform: the
Altinn Events service itself delivers at-least-once and unordered (competing consumers, no Service
Bus sessions, and per-event retry parking up to 12h — see the ordering section of the ADR), so
ordered registration was never observable by subscribers. Consumers that mirror process state from
Altinn events must tolerate out-of-order (and duplicate) delivery. Should a side effect ever
genuinely need to run after another, express it with an explicit `DependsOn` between the siblings —
never by step order. Note also that process-end events may register before the process-end cleanup
commands (deletes) finish, since the side-effects workflows start at the commit.

Post-commit categorization: `ExecuteServiceTask`, `EndProcessLegacyHook`,
`DeleteDataElementsIfConfigured`, and `DeleteInstanceIfConfigured` are **critical** (stay in Main);
`MovedToAltinnEvent`, `InstanceCreatedAltinnEvent`, `CompletedAltinnEvent`, and
`NotifyInstanceOwnerOnInstantiation` are **side effects**.

### Task-to-Task Transition (e.g., Task_1 → Task_2)

```text
Main workflow:
── instance.Process.CurrentTask = Task_1 (OLD) ──
EndTask → CommonTaskFinalization → OnTaskEndingHook → LockTaskData
  ── MutateProcessState (in-memory: CurrentTask → Task_2) ──
── instance.Process.CurrentTask = Task_2 (NEW) ──
UnlockTaskData → CleanupGeneratedFromTask → OnTaskStartingHook → CommonTaskInitialization → StartTask
  ── SaveProcessStateToStorage (persist to Storage) ──
EnqueueSideEffectsWorkflow → [ExecuteServiceTask if service task — one engine step per pipeline stage, then
                              the concluding one; or, if the pipeline opens a mailbox, MintMailbox immediately
                              before the declaring stage, the stages, and then EnqueueReceiveWorkflow instead
                              of the conclusion]

Side-effects workflow (single-step independent root, IsHead=false, own commit-time state, links→Main):
MovedToAltinnEvent

Mailbox receive workflow (only for a mailbox pipeline; single-step head, DependsOnHeads=false, own
mailbox declaration, fresh callback token): the pipeline's conclusion
```

### Task-to-End Transition (e.g., Task_1 → EndEvent)

```text
Main workflow:
── instance.Process.CurrentTask = Task_1 (OLD) ──
EndTask → CommonTaskFinalization → OnTaskEndingHook → LockTaskData
  ── MutateProcessState (in-memory: CurrentTask → null, EndEvent set) ──
OnProcessEndingHook
  ── SaveProcessStateToStorage (persist to Storage) ──
EnqueueSideEffectsWorkflow → EndProcessLegacyHook → DeleteDataElementsIfConfigured → DeleteInstanceIfConfigured

Side-effects workflow (single-step independent root, IsHead=false, own commit-time state, links→Main):
CompletedAltinnEvent
```

### Initial Task Start (process just created)

```text
Main workflow:
── instance.Process.CurrentTask = Task_1 (already set by CreateInitialProcessState) ──
UnlockTaskData → CleanupGeneratedFromTask → OnTaskStartingHook → CommonTaskInitialization → StartTask
  ── SaveProcessStateToStorage (persist to Storage) ──
EnqueueSideEffectsWorkflow → [ExecuteServiceTask if service task — one engine step per pipeline stage, then the concluding one]

Side-effects workflows (one single-step independent root per effect, IsHead=false, own commit-time state, links→Main):
MovedToAltinnEvent ∥ [InstanceCreatedAltinnEvent if instantiation] ∥ [NotifyInstanceOwnerOnInstantiation if configured]
```

### Task Abandon (reject → end)

```text
Main workflow:
── instance.Process.CurrentTask = Task_1 (OLD) ──
AbandonTask → OnTaskAbandonHook
  ── MutateProcessState (in-memory: CurrentTask → null or next task) ──
[OnProcessEndingHook if ending] / [task-start commands if moving to next task]
  ── SaveProcessStateToStorage (persist to Storage) ──
[EnqueueSideEffectsWorkflow if the target emits side effects] → [critical post-commit commands]

Side-effects workflows (only when the target emits side effects, one per effect):
[side-effect commands]
```

### Side-effect failure observability and redrive

Side-effect failures never gate anything and never surface in the ProcessNext result **or** the
read-path `workflow` status annotation: a failing event registration retries per the engine's step
retry strategy (production default: exponential backoff up to 24h `MaxDuration`) and then lands as
a terminal `Failed` workflow that nothing waits on and no user ever sees. A terminally failed
side-effects workflow means outbound events/notifications were **lost** — downstream event
subscribers never learn of the transition — so this class must be monitored explicitly:

- **Alert** on the engine metric `engine.workflows.execution.failed` with `reason` in
  (`execution`, `poisoned`) across **all** `is_head` values — every terminal failure needs ops.
  There is no user-facing Retry for terminally failed workflows (the failed screen shows error
  details + contact support; the frontend recovers on its own once the workflow is resumed), so
  an ops resume is the only recovery path. Use `is_head` to route/prioritize, not to filter:
  `is_head="false"` means a side-effects workflow failed — outbound events were lost, re-deliver
  via the engine resume; `is_head="unset"` (or `"true"`) means a head (Main) workflow failed — the
  instance is stuck for the user until ops resumes it (cascade) via `process/resume`. Do **not**
  alert on `reason="dependency_failed"`: a side-effects workflow has no dependencies and never
  lands there; the increments come from dependent Main workflows (auto-advance chains) condemned by
  an upstream Main failure that already fired the alert, and the cascade resume of that failure
  revives them.
- **Enumerate** with `GET /api/v1/{org}/{app}/workflows?status=Failed` — side-effects workflows are
  identifiable by `isHead: false` on the status response (their OperationId also carries the
  human-readable `Process next side-effects:` naming prefix and names the one effect it carries,
  e.g. `… · MovedToAltinnEvent`), or scope to one instance by
  `collectionKey`/`processNextInstanceGuid` label.
- **Redrive**: resume the failed workflow via the engine's resume API — a resumed side-effects
  workflow re-runs its remaining steps and re-delivers its events (event registration is
  idempotent per event). A side-effects workflow exists only for a **committed** transition and
  carries its own commit-time state, so a redrive is always valid — there is no
  "correctly dead" case to distinguish. Note that the app's `POST process/resume` deliberately
  does **not** touch side-effects workflows (they are excluded from the resume-target lookup); the
  engine-level resume is the only re-emit path. The Main workflow it belongs to is reachable via
  the workflow's `links`. The redrive window is implicitly bounded by the engine's
  terminal-workflow retention sweep (default 60 days): after that the failed workflow — including
  the state a resume would need — is purged.

## Waiting, Failure Classification, and Reject/Resume

`WorkflowEngineService` does more than fire-and-forget. After enqueueing it polls the workflow **collection** (keyed by the instance guid — every transition of an instance shares one collection) until the active heads settle, then refetches the instance and builds a `ProcessNextWorkflowResult`:

- **A parked chain releases early.** When every active workflow in the anchored chain is `Waiting` (a service task deferred), the wait releases with the ordinary success shape after a short grace window (~2s, so near-instant polls still complete synchronously). Deferral is post-commit by construction (only `ExecuteServiceTask` defers, after `SaveProcessStateToStorage`), so the instance already carries the committed target task; the read-path `workflow` annotation and the frontend waiting UI take over from there. A committed-state guard makes a hypothetical pre-commit deferral fall through to the ordinary timeout instead. The 100s timeout (504/`Timeout`) is thereby reserved for chains that are genuinely slow or stuck.

- `ScopeToCurrentChain` narrows the collection to the workflow just submitted and everything created after it, so lingering terminal heads from earlier transitions don't leak into the current wait. It also strips side-effects workflows (matched by the engine-persisted `isHead == false` head-visibility directive; the `Process next side-effects:` OperationId prefix is a naming convention only) from every path: they must not extend the wait — they are enqueued mid-Main, so they are strictly newer than the anchor and would otherwise leak into the chain — and their failures must never be classified as transition failures.
- `BuildWorkflowFailure` classifies the outcome into a `WorkflowFailure` (`StepFailed`, `DependencyFailed`, `EngineFault`, `Timeout`, or a superseding-abandon case). `ExtractCallbackErrorDetail` unwraps the ProblemDetails `detail` from an engine error message so the human-readable reason is available server-side (logged by the controller); the raw message is never serialized to clients — failed action responses ship a stable generic `detail` plus a `workflowFailure` stripped of its recorded error.
- `HasCommittedProcessState` reports whether `SaveProcessStateToStorage` completed, so the caller knows if the transition was persisted even when a later step failed.

`GetCurrentTaskWorkflowState` returns a closed set — `Unblocked`, `Retrying(workflowId, collectionKey)`, or `ResumeRequired(workflowId, collectionKey)` — used before enqueueing a new action so a still-running or terminally-failed transition blocks the next action.

`ResolveWorkflowTaskStatus` is its read-path sibling: a presentation projection (idle / processing / failed + target task + failure kind, plus the failed workflow id/timestamp as a support reference) used by `ProcessStateEnricher` to annotate every process/instance read. A transition parked on a deferring service task additionally carries `waitingReason` — the task's own words from its most recent `Defer`, passed through from the engine's collection-head view — so a waiting UI can say what is being waited for. The frontend renders a terminal failure as an error page carrying that support reference — deliberately **no user Retry** (the engine already exhausted its retry budget) and no polling (the failed page is static — a terminal failure needs manual intervention either way); recovery is ops calling `POST process/resume` followed by the user refreshing the page. **Known gap:** for an ended process (`CurrentTask == null`) it reports idle without consulting the engine, so a terminal failure in the final transition's post-commit steps (which run after `ended` commits) never surfaces on a read — detection is ops alerting on the engine's failed workflows.

Reject/resume/abandon:

- `ResumeAndWaitForWorkflow` resumes a failed workflow (cascade) and waits for it to settle — sharing the wait above, so a resumed workflow that immediately defers again also releases early with the waiting UI.
- `AbandonWorkflow` writes off a terminally failed workflow (`Failed → Abandoned`) so a subsequently enqueued workflow can depend on it; returns `false` if the engine's compare-and-set was rejected (e.g. a concurrent resume revived it).
- `EnqueueDependentProcessNext` enqueues a workflow that `dependsOn` another (used by the reject flow to supersede a failed transition, and by auto-advance).

## State Passthrough

Each callback needs the app's workflow callback state (`instance` + `formData`). Rather than fetching from Storage on every callback (which would see stale process state), the app captures that state into a **signed** opaque string that the engine stores and echoes back with each callback.

**Signing**: `WorkflowStateSigner.Sign` wraps the serialized `WorkflowCallbackState` in a `SignedWorkflowState` envelope with a detached HMAC-SHA256 signature and the `secretId` of the signing code. Every `Sign`/`Verify` names a `SigningDomain` (see `SigningPurpose`), and the state blob's is `CallbackState`, which is **underived** — signed with the app-code directly, so blobs signed before domains existed still verify. That is pinned by known-answer vectors in `WorkflowStateSignerTests` rather than by round-trips, which would agree with themselves after any change. `Verify` re-computes the signature (constant-time compare), rejecting tampering, unknown/expired secrets, and malformed envelopes — all mapped to a non-retryable 422. The blob's signing lifetime tracks the callback token's (same clock skew), so blob and token fail together during code rotation.

**Flow**:

1. `WorkflowCallbackStateService.CaptureState` → serializes instance + form data (+ the carry's contents) into `WorkflowCallbackState`, then signs it → string
2. The signed string is included in `WorkflowRequest.State`
3. Engine echoes it back in `AppCallbackPayload.State` for each callback
4. `WorkflowCallbackStateService.RestoreState` → verifies the signature, deserializes, asserts the blob's instance matches the callback route instance, then returns an `InstanceDataUnitOfWork` with preloaded form data plus the `WorkflowCallbackStateCarry` the blob was holding
5. After command execution, the updated state — data _and_ carry — is captured, re-signed, and returned in `AppCallbackResponse.State`
6. Engine uses the returned state for the next callback — state evolves command by command. For a **deferred** step the app echoes the incoming state back unchanged (deferral is stateless — the controller rejects a deferring handler that made data changes), and the engine hands a deferred step its own returned state on the next attempt (`ResolveStateIn` prefers a step's own `StateOut`), so every re-check starts from exactly the state the step first received.

**Capture point**: `ProcessEngine` captures state BEFORE the in-memory process state is mutated to the next task. The blob carries the OLD process state (CurrentTask = the task being left). `MutateProcessState` transitions the in-memory state to the new task between the two command groups.

**Side-effects workflow state**: the side-effects workflow carries the **commit-time state blob** as its own `State`. `EnqueueSideEffectsWorkflow` runs immediately after `SaveProcessStateToStorage`, so its `StateIn` — the blob it forwards — is exactly the state the transition committed: the (NEW) process state plus every data change made up to the commit. Side-effect commands therefore always act on committed data, even when the transition ended the process and the instance was auto-deleted from Storage. (They do not see changes made by _later_ critical post-commit commands such as `ExecuteServiceTask` — the events describe the commit, not what happened after it.)

**Why commands read from `instance.Process.CurrentTask`**: In the old ProcessEngine, task-end/start handlers received `taskId` as an explicit parameter. The new commands read directly from `instance.Process.CurrentTask` — single source of truth. `MutateProcessState` ensures each command group sees the correct CurrentTask.

## How to Add a New Command

1. **Create the command class** in the appropriate `Commands/` subfolder:
    - Without payload: implement `IWorkflowEngineCommand` directly
    - With typed payload: extend `WorkflowEngineCommandBase<TPayload>` and create a `record TPayload : CommandRequestPayload`

2. **If using a payload**: register it in `CommandPayload.cs`:
    - Add `[JsonDerivedType(typeof(MyPayload), typeDiscriminator: "myPayload")]` to `CommandRequestPayload`
    - Add `[JsonSerializable(typeof(MyPayload))]` to `CommandPayloadJsonContext`

3. **Register in DI**: add `services.AddTransient<IWorkflowEngineCommand, MyCommand>()` in `ServiceCollectionExtensions.cs`

4. **Add to sequence**: add to the appropriate method in `WorkflowCommandSet.cs` (use `AddCommand` for pre-commit, `AddCriticalPostCommitCommand` for post-commit work the transition must wait on, `AddSideEffectCommand` for fire-and-forget post-commit work that runs as its own non-gating single-step side-effects workflow). Side-effect commands see the commit-time state (the exact state `SaveProcessStateToStorage` persisted) — but remember the only timing guarantee is that they never gate the transition: they are independent roots the engine may start as soon as they are enqueued at commit, possibly before the process-next response is sent, in parallel with Main's critical post-commit commands _and with each other_, and they must stay idempotent and non-blocking.

5. **Startup validation**: `WorkflowEngineCommandValidator.Validate` will fail at startup if a key in `WorkflowCommandSet` isn't registered in DI

## Command Conventions

- Every command has `public static string Key => "..."` and `public string GetKey() => Key`
- Commands return `SuccessfulProcessEngineCommandResult`, `DeferredProcessEngineCommandResult` or `FailedProcessEngineCommandResult` (never throw from Execute). `FailedProcessEngineCommandResult` distinguishes `Retryable` (→ 500, engine retries) from `Permanent`/`NonRetryable` (→ 422, engine gives up). `DeferredProcessEngineCommandResult` is neither: it returns 200 with a `defer` block, so the engine parks the workflow in `Waiting` and re-executes the step later — no error recorded, retry counter reset. Today only `ExecuteServiceTask` produces one (from `ServiceTaskResult.Defer`); the app-facing contract, the wait budget (`ProcessStepOptions.WaitBudget`) and the two clock groups a task reads to pace itself (`context.Attempt` for this execution, `context.Wait` — incl. the derived `Remaining`/`IsFinalCheck` — for the whole wait) are documented on those types. For send-then-poll (or any multi-phase) tasks: implement `IPipelineServiceTask`, give each earlier phase its own stage and let `Finally` conclude — the engine's step ledger is the durable send guard (a completed stage never re-runs; a retry or resume re-enters at the failed stage), never anything under `Attempt`/`Wait`; `StepId` (per stage) is the outbound idempotency key covering the in-attempt crash window (see the `Defer` xmldocs). `EFormidlingServiceTask` is the worked example in-tree: a send stage, a polling `Finally` that owns the wait budget, a backoff ladder driven by `Wait.DeferCount`, and a `FailedPermanent` on `Wait.IsFinalCheck` that names what never arrived instead of expiring generically
- **Pipeline service tasks**: every service task IS a pipeline — `IPipelineServiceTask` is the root contract (`Define(builder)` composes `Stage(name, work, options?)*` + exactly one terminal — `Finally(work, options?)`, or `ConcludeOnReply`/`ConcludeOnReplies` when a stage opened a mailbox; the builder's types make any other shape uncompilable), and `IServiceTask` derives from it with a **sealed forwarding default**: `Define => pipeline.Finally(Execute)`. The runtime therefore has exactly one dispatch path (resolve pipeline via `ServiceTaskLookupExtensions.ResolvePipeline`; a stage name dispatches to that stage, a null one to the pipeline's conclusion), and the simple task's concluding-step semantics are a derived fact, not a special case. The factory expands one `ExecuteServiceTask` engine step per stage at enqueue time (payload carries the stage name; OperationId is `ExecuteServiceTask: {stageName}` (printable ASCII only — stage names travel in the engine's `Operation-Id` HTTP header, so the builder rejects anything else)), then the concluding step with a null stage name and the bare OperationId — for an `IServiceTask` that concluding step is the whole expansion. The expansion fixes the pipeline's shape for the workflow's lifetime — stage names are explicit literals and a compatibility surface for in-flight workflows (renaming the work method is refactor-safe; removing/renaming the literal strands callbacks with permanent `ServiceTaskStageNotFound`). Stages share state through the ordinary mechanism only: a completed stage's data changes are saved into the state blob the engine hands the next stage — no separate handoff channel, and a deferring attempt saves nothing. Options: a step's own builder options — a stage's from `Stage`, the conclusion's from whichever terminal ended the chain — win field-wise over the task's own, which are the fallback for every step; declare a polling pipeline's wait budget on `Finally`, since a budget on the task also reaches stages that never wait. Registration: `AddTransient<IServiceTask, …>` or `AddTransient<IPipelineServiceTask, …>` per the implemented interface (the type system forbids the wrong pairing; lookups union both). `ServiceTaskRegistrationValidator` fails startup on a throwing/null `Define` (the builder rejects duplicate, empty and non-ASCII stage names, bad options, a second mailbox, a handle from another pipeline or answered twice, and a mailbox opened but left unanswered — all eagerly, from the composing call itself) and on an `IServiceTask` replacing the sealed `Define` (backstop for analyzer rule `ALTINNAPP0700`). `Define` must be cheap/deterministic/side-effect free — it runs at enqueue, on every callback, and at startup. Gotcha: Moq mocks bypass the forwarding default (null pipeline → legible failure); use real fakes in tests
- Commands get instance data through `context.InstanceDataMutator` (an `InstanceDataUnitOfWork`)
- Commands pass `context.CancellationToken` into app-facing contexts (`ProcessTaskContext`, hook contexts, and `ServiceTaskContext`)
- The callback controller saves data changes after successful execution - commands don't need to persist data themselves (except `SaveProcessStateToStorage`, which writes to the process/events API)
- Hook commands (`OnTaskStarting`, `OnTaskEnding`, `OnTaskAbandon`, `OnProcessEnding`) enforce max 1 handler per task
- `ExecuteServiceTask` can request auto-advance by returning a `ServiceTaskSuccessResult` with `AutoAdvanceProcess = true`; it maps this to a `SuccessfulProcessEngineCommandResult { AutoAdvanceProcess = true, AutoAdvanceAction }`, and the callback controller enqueues a dependent process-next workflow after the save

### Mailboxes

- **Declaring one — the composition surface.** A pipeline answered by a message rather than by polling opens one from the stage that sends: `pipeline.Stage("<stage>", work, new MailboxOptions { Timeout = … }, out MailboxHandle handle)`, ended by `ConcludeOnReply(handle, onMessage, onClosed)` or `ConcludeOnReplies(handle, onMessage, onClosed)`. The declaration is a **`Stage` overload**, not a modifier on the composed pipeline: the declaration and the mailbox-aware delegate must travel together (a modifier applied after the fact cannot retype an already-supplied delegate), and an overload has no "modifier with no stage to attach to" error path to guard in the first place. Internally the stage is a `ServiceTaskStage.MailboxOpening` holding the `MailboxOptions` as its `Declaration`; `ServiceTaskStage` is a closed two-member hierarchy (`Plain` / `MailboxOpening`), so each shape's work delegate takes exactly the arguments it needs and no execution reads a nullable declaration to rediscover which kind of stage it is running. The `MailboxHandle` the overload hands out is opaque and impossible to construct, which makes "a reply terminal answers a really-declared mailbox" a **compile-time** fact rather than a runtime string lookup; the builder adds only what types cannot say — the handle belongs to this builder, it is answered exactly once, and `Finally` refuses outright once a stage has opened a mailbox (a final step would conclude the task before any message arrived) — all eagerly, so a mistake is an app startup failure rather than a callback failure days later. Nothing guards a discarded return any more: a terminal is the only way to obtain the `ServiceTaskPipeline` that `Define` must return, so no return value can be discarded to lose a declaration. That is not the same as nothing being droppable, though: `ServiceTaskPipelineBuilder`'s constructor is public, so a `Define` that ignores the builder it was handed and returns a pipeline built on a fresh one of its own drops the declaration silently — no eager throw, no mint step, precisely the case the deleted `ResolvePipeline` check covered. Making that constructor `internal` is the cheap close, and is recorded as a follow-up rather than done here. **One builder type, no intermediate chain types, handles rather than a mailbox-flavoured builder** is a settled decision rather than an oversight: a second builder returned by the overload would make most of those eager checks structural instead, but the later multi-exchange phase needs handles to say *which* exchange a terminal answers, so a handle-free phase 1 would only have to reintroduce them a phase later. **A task gets one exchange in this version:** a second mailbox-opening stage is an eager throw, and two exchanges are two BPMN tasks for now.
- **The mint is its own engine step**, `MintMailbox` (OperationId `MintMailbox: {stageName}`), emitted immediately before its declaring stage. Its position is load-bearing in both directions: the deadline clock starts at the mint, so no earlier stage may erode the exchange's budget, and the stage must never send without an address, so nothing may mint after it. A step of its own rather than part of the stage's execution because the mint's outcome is durable and the stage's is not — the mint completes once and never re-runs, while the stage after it may fail, defer and re-run against the address already published. It mints via `POST {engine}/{ns}/mailboxes` keyed on **its own** `StepId` (the step id the engine sent it on that callback — pinned end to end by asserting the mint step's `databaseId` equals the mailbox's `idempotencyKey`), with the instance guid as `collectionKey`, so a replayed attempt of that step is handed the mailbox the first attempt published instead of minting an orphan. Mint outcomes are modeled as `MailboxMintResult`: `Minted` (201/200, replay not distinguished) records the mailbox in the carry; `Rejected` (400 → permanent `MailboxRejected`, most often a `Timeout` past the engine's `MaxMailboxTimeout`, which app startup cannot check because the limit is the engine's); `AtCapacity` (429 → **retryable** `MailboxAtCapacity`, carrying the engine's detail so the first failure names the at-cap collection rather than a bare status). An empty `StepId` is a permanent `MailboxStepIdMissing` (an empty key is a constant, so it would collapse every mailbox in the namespace onto one shared inbox). A stage that no longer opens a mailbox — renamed, moved to another stage, or withdrawn since this workflow was enqueued — is a permanent `MailboxDeclarationNotFound`: one guard instead of the two it replaced — a missing stage and a missing declaration are the same miss now that the declaration lives on the stage — and the wording names where the mailbox went before telling the reader to restore the old name. Every other mint failure rides the step's retry ladder, which is safe because the stage after it has not run — with one known wart, recorded as a follow-up rather than fixed: a service task type missing from DI throws `ProcessException` from inside the same `try`, so a redeploy that renamed the task away retries without ever converging. `ExecuteServiceTask.Execute` has the identical shape — same throw, same outer catch — so that wart belongs to the pipeline runtime at large, not to the mint.
- **Reading it in the declaring stage.** `ExecuteServiceTask` mints nothing any more; it reads the carry. Its `Execute` is a **three-way dispatch resolved once** — `ExecuteStage` (the payload carries a stage name), `ExecuteReply` (null stage name, `ReplyExchange` conclusion) and `ExecuteConclusion` (null stage name, `FinalStep`) — each branch a method that assumes its shape rather than interrogating nullable fields to rediscover it. The declaring stage's work is handed a non-nullable `ServiceTaskMailbox` (the `Id` it publishes plus the absolute `Deadline`) read from the carry; a missing entry is a permanent `MailboxIdMissingFromState` naming both of its causes — a redeploy that *added* the declaration while a workflow enqueued against the declaration-free shape was in flight (that workflow's step list holds no mint step at all), or the mint step's record not surviving into this step's state. A stage handed a mailbox rendezvous is a permanent `MailboxReceiptOnStage`: rendezvous only ever ride a receive workflow's one step, so this is a workflow this app-lib's expansion did not build.
- **The expansion changes shape for a declaring pipeline:** the conclusion is _not_ emitted as a Main step (it is the reply handler, and runs on each receive workflow instead — emitting it here too would conclude the task a second time, on nothing), and Main instead ends with an `EnqueueReceiveWorkflow` step, appended after every critical post-commit step. That step enqueues **receive workflow 1** — one workflow whose single step is the pipeline's conclusion, carrying the engine's `mailbox` declaration, enqueued as a collection head that depends on no head, with a callback token minted at _its_ execution and with this step's own state blob. Its payload carries the `OpeningStageName`, set at assembly time and never re-derived at this hop (a stage renamed mid-flight would otherwise address a different mailbox, or silently none), and the command looks the mailbox up in the carry by that name — which leaves a broken carry as the only cause of a `MailboxIdMissingFromState` here, since this step and the mint step are emitted by the same expansion and a redeploy cannot leave one without the other. **Minting the token there buys per-hop freshness for the relay's later hops, not a longer-lived receiver 1:** `GenerateToken` sets `Expires` to the _signing code's_ expiry and `GetSigningSecret` returns the first non-expired code in configuration order, so a mint seconds after the transition's enqueue picks the same code — and the receiver's state blob was signed by that code too, which `WorkflowStateSigner` rejects once it expires. Receiver 1's token and its blob both die at the app code's `ExpiresAt` — the general bound on any parked workflow described under Key Design Constraints above, which nothing here checks a declaration against. The engine's `MaxMailboxTimeout` is the only ceiling a `MailboxOptions.Timeout` is actually measured against, and it is enforced by the mint (`MailboxRejected`), not by this command. It is a step of Main, and the last one, on purpose: the receiver exists before Main settles, so the instance's collection never reads all-settled while an exchange is open — the **frontier-never-empty** convention that everything gating on the collection (the process-next wait, `ResolveWorkflowTaskStatus`, auto-advance) relies on without knowing mailboxes exist. `Held` accordingly counts as an _active_ and _parked_ status in `WorkflowEngineService`: a Held receiver blocks the next action and reads as `Processing`, and the process-next wait releases early with the ordinary success shape exactly as it does for a deferring service task. No waiting reason is persisted — the wording is static per task and lives in the pipeline definition.
- **The carry:** the mint is keyed on the mint step's own `StepId`, which no later step can re-derive, so the mailbox travels in the signed state blob. `WorkflowCallbackState.mailboxes` is a **map keyed by the opening stage name**, each entry holding an `id` and a `deadline` (`"mailboxes": { "SendToArchive": { "id": "018f4e…", "deadline": "2026-08-30T12:00:00Z" } }`) — a map from day one, so the later multi-exchange phase needs no blob-format migration against in-flight workflows, and `null` rather than an empty map when nothing travels, so a workflow with no exchange publishes the blob it always did. One test pins those literal field names, because the round-trip tests use the same serializer both ways and would agree with themselves after a rename that broke every in-flight workflow. `WorkflowCallbackStateService.RestoreState` returns the map beside the unit of work as a `WorkflowCallbackStateCarry`, the callback controller threads that object into `ProcessEngineCommandContext.StateCarry` and back into `CaptureState`, and a command that never touches it forwards it unchanged. Its API is three methods, each named for the one thing it records: `RecordMailbox(stageName, id, deadline)` (the mint step — re-recording the *same* mailbox is a mint replay and is accepted; a *different* mailbox for the same stage is unreachable by construction and throws rather than picking a winner), `FindMailbox(stageName)` (the declaring stage and the enqueue step; named for the local `ServiceTaskPipeline.FindStage` convention, since `TryGet*` in .NET means `bool` + `out`) and `RecordMailboxConcluded(stageName)` (the relay). Nothing in the carry assumes the map holds at most one entry, even where today's builder does. A deferral is stateless as ever, but a declaring stage that defers no longer re-mints on its next attempt: the mint step is already complete, and the blob a deferral echoes back still carries its entry, so the retry is handed the same address

### The reply handler and the relay saga

- **The rendezvous, and the guards that run before the handler.** On a receive workflow the pipeline's conclusion runs once per rendezvous, and **the message and the closure arrive as delegate parameters, not as context getters** — `onMessage(context, ServiceTaskReply)` for a delivered message, `onClosed(context, MailboxClosedReason)` when the mailbox closed with the task still unconcluded. That is why `ServiceTaskContext` is a plain record again: there is no `Mailbox`/`Reply`/`ReplyClosedReason` getter that throws outside the one execution it is valid in, and so no hand-written `PrintMembers` keeping `ToString` from throwing. Which handler runs is decided by the engine's rendezvous, never inferred: exactly one of a delivery and a disposed reason is present, and a rendezvous carrying neither or both fails the step permanently (`MailboxReceiptAmbiguous`) rather than being read as a closure — an absent message *is* the instruction to conclude, so "neither" must not quietly mean closed. An empty message is a `ServiceTaskReply` with an empty `Payload`, never a null; the engine tells the two apart and the app-lib never infers one from the other. `MailboxClosedReason` says whether the mailbox closed by `Deadline` or by `Request`, for the wording only — both mean no message can arrive, and both demand the same response. The remaining guards on this path are all permanent, and they split on reachability: a reply-answered pipeline handed no rendezvous (`MailboxReceiptMissing`) and a `Finally`-concluded pipeline handed one (`MailboxReceiptWithoutDeclaration`) are redeploy or engine drift, unreachable from app code, which is why they survived the compile-time move; a delivery that does not open as something this application sealed (`MailboxDeliveryEnvelopeInvalid`) is **not** — `IServiceTaskReplyForwarder` takes the mailbox id and the service task type from its caller, deliberately, so forwarding under the wrong one seals for a different mailbox or handler and fails the unwrap here. Its other routes are a forged or altered delivery and an app code that expired while an early message waited unread at its position, which needs nothing to be wrong with the message at all — hence the wording naming it.
- **The verdict vocabulary is split at compile time rather than checked at runtime:** `ConcludeOnReply`'s `onMessage` returns `ServiceTaskResult`, so its one message concludes the task and `AwaitNextReply` **does not compile** there; `ConcludeOnReplies`'s `onMessage` returns `ServiceTaskExchangeResult`, the re-rooted supertype that adds `AwaitNextReply()`; and `onClosed` returns `ServiceTaskResult` on both, so asking for another message on a closed mailbox is unrepresentable. That is where the old `AwaitNextReplyOutsideAnExchange` and `MailboxExchangeAlreadyClosed` runtime failures went — deleted with the shapes that could express them, not reimplemented defensively. Single and multi are not recorded on the internal model: the split did its work at the API boundary, and a single-message handler wraps losslessly into `PipelineConclusion.ReplyExchange.OnMessage` because its results are a subtype, so the runtime treats every exchange uniformly. The verdicts themselves: `AwaitNextReply()` handles this message and leaves the exchange open, `Success(action?)` / `FailedPermanent` conclude it, `FailedRetryable` retries this message with the saga unstarted, and `Defer` parks the receiver against the same frozen message.
- **A result type the runtime has no move for is a permanent failure that names the type, never a throw:** all three unmappable-result sites — `MapStageResult`, `MapServiceTaskResult` and `MailboxRelay.Decide`'s `default` — return `FailedProcessEngineCommandResult.Permanent(…, "ServiceTaskResultUnknown")`, because a throw would be caught by `ExecuteServiceTask.Execute` into a *retryable* failure that can never converge on an author mistake. Those arms are reachable from app code, which is why they are not `UnreachableException`s: the result roots declare no constructor an app can call, but they are records, and C# forbids narrowing a record's synthesized copy constructor below `protected`, so chaining that still compiles. `Decide`'s arm deliberately does **not** close the mailbox — what closes it in that switch is the app having *concluded* the exchange, and an unrecognised verdict is no conclusion; the runtime cannot tell which of `Success`, `FailedPermanent` or `AwaitNextReply` was meant, and closing picks the most destructive reading, losing the answer even after the author fixes the bug. Left open, the deadline still bounds it, an operator can close it by hand, and a resume replays the message into the corrected handler.
- **The saga lives in exactly one place, `MailboxRelay`**, never in app-author code: `Decide` maps the verdict to the callback's outcome plus a `MailboxContinuation` (a two-member closed set — `AwaitNextMessage` has no path to a closure and `Conclude` none to a successor, which is how "at most one execution concludes" is structural rather than reviewed), and `Continue` performs it. `Continue` runs from the **callback controller after the save and re-capture**, because whatever it starts must begin on the state the handler _published_ — a successor started on the incoming blob would miss its predecessor's data and their Storage-assigned ids — and because re-capturing re-signs the blob with whatever app code is current at that hop, which is the only thing that lets an exchange outlive the code that opened it. `Conclude` **closes the mailbox before enqueueing the after-workflow**, in one method, because the reverse order compiles and would let a message land in an exchange already concluded; a permanent failure still closes (run before the response, so a retry repeats it) but starts nothing.
- **What every enqueue is keyed on, and what the successor carries.** Every enqueue is keyed off the executing `StepId` — `{stepId}:mailbox-receive` for the successor, `{stepId}:mailbox-after` for the after-workflow — so a crashed attempt's replay deduplicates instead of forking the relay. The successor is enqueued exactly as receiver 1 is (a head that depends on no head, the same mailbox declaration, a token minted at that hop, the transition's lock token verbatim), which is the **frontier-never-empty** convention's second half: at no instant between the exchange's start and its conclusion does the collection read all-settled. The successor also carries the transition's labels, re-derived from the committed instance: not decoration, because `ResolveWorkflowTaskStatus` reads the task it annotates from `processNextTargetTask`, and `ListCurrentTaskProcessNextWorkflows` — the hop that finds the instance's collection at all — filters on `processNextTargetId`. A successor carrying neither is invisible to that filter, so once retention purges the transition's earlier workflows the lookup finds no collection, answers `Unblocked`, and downstream work starts on top of an open exchange. `processNextSourceId` is deliberately absent: it is unrecoverable at a later hop, and no lookup a receiver answers uses it.
- **Concluding, and what the blob stops carrying.** A successful conclusion also calls `WorkflowCallbackStateCarry.RecordMailboxConcluded(openingStageName)`, so the blob it publishes drops that stage's entry; a permanent failure does not need to, because a failing callback publishes no blob for the carry to un-say anything in. **What that protects is one stage, not the whole blob:** `RecordMailbox` refuses a conflicting re-record *per stage*, so the case it prevents is the next transition opening a mailbox from a stage of the *same name* and being refused over an entry days out of date — there is no "one mailbox per blob" rule left to trip over. The stage name reaches `Decide` as a parameter, sourced from `PipelineConclusion.ReplyExchange.OpeningStageName` — deliberately not through `MailboxRelayRequest`, which exists only on the `Continue` path and therefore only *after* `CaptureState`: routing the carry write through there would publish a blob still naming the concluded mailbox. `MailboxRelay.Decide` refuses `AwaitNextReply` and an auto-advancing `Success` outright when the engine sent no `StepId` (`MailboxStepIdMissing`, the same guard the mint and the first receiver's enqueue carry): an empty id is a constant, and engine idempotency is scoped to `(namespace, key)`, so every exchange in the application would collapse onto one successor and one after-workflow. The guard is narrow on purpose — a conclusion that starts nothing, a retryable failure and a deferral make no keyed call, and refusing those would fail a working callback over a key it never uses. **Two enums with identical members exist on purpose:** `Models.Engine.MailboxDisposedReason` is the wire shape (public only because it hangs off the already-public `AppCallbackPayload`, which MVC model-binds) and `Features.Process.MailboxClosedReason` is what app code reads; do not merge them, or the app's vocabulary becomes a wire type the drift guard owns

### Forwarding a received message

`IServiceTaskReplyForwarder` (public; `ServiceTaskReplyForwarder` behind it, registered transient — the xmldoc tells subscribers to resolve it per message from a scope) is how an external system's answer reaches the mailbox waiting for it. It takes the **mailbox id** the system echoed back, the **service task type** whose handler reads the message, the body, and the source's **own message id**; it seals the body into a `MailboxDeliveryEnvelope` and `POST`s the delivery with that message id as the engine's `idempotencyKey` — the same value the handler reads back as `ServiceTaskReply.IdempotencyKey`, so the platform's deduplication and the handler's are about one string. **There is no lookup and no round trip:** the receive workflow's shape (its handler, its step options) was declared by the app-lib at receiver-enqueue time, so a delivery is an address, a key and a body — and the service task type is _supplied by the caller_ rather than derived, because a derivation can be wrong at signing time and then sign its own mistake, producing an envelope that verifies perfectly against the wrong handler (a defect recorded against an earlier design of this feature). **The envelope's domain (`SigningPurpose.MailboxDeliveryV1`) binds the mailbox id, the service task type and the idempotency key**, each closing one move available to a holder of engine API credentials: re-delivering a captured message into another mailbox, enqueueing a receiver against _this_ mailbox that names another task's handler, and re-delivering the same envelope under a fresh key. The tag is **length-prefixed** (counting `String.Length`, the unit it is written in) so two free-form fields cannot be re-split; the state-blob domain stays **underived** so in-flight blobs survive. `ExecuteServiceTask` unwraps at the receiving end using the three values the _delivered_ callback carries — a payload that does not open is a permanent `MailboxDeliveryEnvelopeInvalid` and the handler never runs, because the bytes at that position never change. **The status mapping lives in the forwarder and nowhere else**: `202`/`200` are both success (the source redelivering, and a retry of the forwarding call itself), `404` is `Unroutable`, `409` is `Late` — _always_ too late, never too early, since deliveries precede receivers happily and the engine has no "too early" answer — `413` is `PayloadTooLarge`, `429` is `MailboxFull`, any other 4xx is `Rejected`, and anything else is `EngineUnavailable`. Only `EngineUnavailable` and `SigningUnavailable` are `IsTransient`: a mailbox's log length never goes back down, and a closed mailbox never reopens. The forwarder **never pre-checks the mailbox's status**, because the engine looks up the idempotency key before its closed check — so a message it already holds replays as `200` even after closure, and a pre-check would dead-letter a message still waiting for its receiver. **The worked example in-tree is Fiks Arkiv** (`Altinn.App.Clients.Fiks`), the feature's first consumer: `FiksArkivServiceTask` opens the mailbox from its `SendToArchive` stage and publishes its id as the outbound message's `klientKorrelasjonsId` — the one Fiks IO field a reply echoes back — and `FiksArkivHost.IncomingMessageListener` reads that echo, decrypts the payloads and forwards them, doing nothing else with the message. Two shapes there are worth copying: the subscriber decides Fiks IO redelivery from `Outcome` per case rather than from `IsTransient` alone, so every verdict is stated rather than defaulted; and its reply-address round trip is pinned by taking the wire value off the _real_ outbound request and echoing that back, because a test that builds its own echo passes whichever field the send wrote it to

## Interaction with Workflow Engine Service

The engine service (a separately-deployed runtime, built from `src/Runtime/workflow-engine` in this monorepo):

- .NET service backed by PostgreSQL
- Receives `WorkflowEnqueueRequest`, stores it, executes steps sequentially
- Returns `WorkflowEnqueueResponse.Accepted` with `DatabaseId` and `Namespace` per workflow
- Calls back to the app via HTTP POST for each app command
- Retries failed steps with configurable backoff (default: exponential, 1s base, 5min max delay, 24h max duration)
- `Namespace` = `{org}/{app}` is the primary isolation boundary; idempotency keys are unique within a namespace
- The instance guid is both the collection key and the `processNextInstanceGuid` label — it groups every transition of an instance
- Steps execute in order; a previous step must complete before the next begins
- `Context` (`AppWorkflowContext`) is opaque to the engine; passed through to command handlers
- Commands use `CommandDefinition` with `type: "app"` and `data: AppCommandData { commandKey, payload }`

### URL Patterns (`WorkflowEngineClient`)

- Enqueue: `POST {ApiWorkflowEngineEndpoint}/{namespace}/workflows` with `Idempotency-Key` header (required) and `Collection-Key` header (optional)
- Collection detail: `GET {ApiWorkflowEngineEndpoint}/{namespace}/collections/{collectionKey}` — returns `null` on 404
- List: `GET {ApiWorkflowEngineEndpoint}/{namespace}/workflows?collectionKey=...&label=key:value&status=...&cursor=...` — paginates through `PaginatedResponse<WorkflowStatusResponse>`
- Cancel: `POST {ApiWorkflowEngineEndpoint}/{namespace}/workflows/{workflowId}/cancel`
- Resume: `POST {ApiWorkflowEngineEndpoint}/{namespace}/workflows/{workflowId}/resume?cascade={bool}`
- Abandon: `POST {ApiWorkflowEngineEndpoint}/{namespace}/workflows/{workflowId}/abandon` — writes off a failed workflow (→ `Abandoned`); 409 means the compare-and-set lost (client returns `false`)
- Deliver: `POST {ApiWorkflowEngineEndpoint}/{namespace}/mailboxes/{mailboxId}/deliveries` with `{ idempotencyKey, payload }` — 202 appended (with the assigned `idx`), 200 the key already delivered one, 404 no such mailbox, 409 closed, 413 payload over cap, 429 log over cap. Every status comes back as a `MailboxDeliveryResult` value; only a transport failure throws

## Authorization and Data Saves

All data saves during callbacks use `StorageAuthenticationMethod.ServiceOwner()`. This is a change from the old ProcessEngine, where data operations used the end user's token.

**Design**: The app (ServiceOwner) performs all data writes during process transitions. The user authorized the action (e.g., "confirm", "reject") at the ProcessNext API entry point. After that, the app executes the transition as ServiceOwner. This means:

- **policy.xml must grant ServiceOwner write rights on all tasks** — this is a prerequisite for the workflow engine
- Storage's authorization service checks the ServiceOwner identity (from the token), not the original user
- The task in Storage's XACML resource comes from `instance.Process.CurrentTask` as persisted in Storage's DB

**Implication for task-start data saves**: Between `MutateProcessState` and `SaveProcessStateToStorage`, task-start commands create/modify data while Storage still has the OLD task as current. This works because ServiceOwner has write access on all tasks. If Storage ever starts forwarding the real userId to the authorization service (e.g., via a header), we would need to persist the process state between the two command groups instead. The factory already separates `taskEndSteps` and `taskStartSteps`, so moving the `SaveProcessStateToStorage` insert point would be straightforward.
