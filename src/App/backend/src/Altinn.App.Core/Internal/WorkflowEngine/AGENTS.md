# Workflow Engine Integration Layer

App-lib integration with the async Workflow Engine service. The engine runs as a separate service; this code handles **submitting workflows**, **waiting for them to settle**, and **receiving callbacks**.

## Architecture

The Workflow Engine service (external, .NET, PostgreSQL-backed) orchestrates process transitions. This integration layer:

1. **Orchestration**: `WorkflowEngineService` (`IWorkflowEngineService`) is the entry point used by the process engine. It builds the enqueue request, submits it, polls the engine until the transition settles, refetches the instance from Storage, and classifies any failure. It also exposes the reject/resume/abandon operations.
2. **Outbound**: `ProcessNextRequestFactory` builds a `WorkflowEnqueueEnvelope` (the `WorkflowEnqueueRequest` body + the metadata that travels via URL path and HTTP headers: namespace, idempotency key, collection key). `WorkflowEngineClient` POSTs it to the engine's enqueue endpoint (`POST {ApiWorkflowEngineEndpoint}/{namespace}/workflows`). Namespace is sent in the URL path; idempotency key and collection key go in HTTP headers (`Idempotency-Key`, `Collection-Key`). Context (`AppWorkflowContext`) carries actor, org/app, instance identification, and the callback token. Workflow execution relies on durable process status and version fences rather than a Storage instance-lock lease. `Namespace` = `{org}/{app}` (isolation boundary); the instance guid is the collection key and is also sent as the `processNextInstanceGuid` label (for querying all workflows for an instance).
3. **Inbound**: The engine calls back to `WorkflowEngineCallbackController` (in the **Altinn.App.Api** project, not this folder) for each app command, one at a time, sequentially.
4. **Per-callback lifecycle**: The controller restores the signed state blob into two halves — an `InstanceDataUnitOfWork` and a `WorkflowCallbackStateCarry` (the non-data bookkeeping: the mailboxes a service task's stages have opened, keyed by the opening stage's item index) — resolves the `IWorkflowEngineCommand` by key, executes it with both, performs one workflow-owned save when the command staged anything (applying replay semantics — see below), captures the updated (re-signed) state from both, and returns it to the engine. A command that never looks at the carry forwards it unchanged, which is how a mailbox id crosses the steps between the mint step that recorded it and the steps that read it. A **deferral** is deliberately different: it is stateless — nothing is saved, the incoming state is echoed back unchanged (the re-run starts exactly where this attempt did), and a deferring handler that made data changes is rejected with a non-retryable 422. A step that checks-and-waits is not a step that records; work that produces something durable belongs in its own pipeline stage.

```text
App ProcessNext API
  → ProcessEngine calls IWorkflowEngineService.EnqueueAndWaitForProcessNext()
      → ProcessNextRequestFactory.CreateChainInitiating()
      → WorkflowEngineClient.EnqueueWorkflows()     (HTTP POST → engine, returns WorkflowEnqueueResponse.Accepted)
      → Poll the workflow collection until it settles, then refetch the instance from Storage
      → Classify the outcome into ProcessNextWorkflowResult (instance, WorkflowFailure?, ProcessStateChanged)

Engine (external service)
  → Executes steps sequentially
  → For each app command: POST to /workflow-engine-callbacks/{commandKey} (echoes the signed state blob)

WorkflowEngineCallbackController.ExecuteCommand()   (Altinn.App.Api)
  → Restore + verify workflow callback state from the signed blob (WorkflowCallbackStateService)
  → Resolve IWorkflowEngineCommand by key
  → command.Execute(context)
  → If successful and there is a mutation plan, save once through SaveWorkflowOwnedAggregate()
  → If Storage reports replay, rebuild the unit-of-work state and continue
  → Capture + re-sign updated state blob
  → On success with AutoAdvanceProcess, enqueue a dependent process-next workflow
  → Return the updated state to the engine
  → (Engine uses the returned state blob for the next callback)
```

## Key Design Constraints

- **ALL commands MUST be idempotent** - the engine retries failed commands with configurable backoff
- **A chain-initiating enqueue is fenced by one authoritative Storage snapshot.** Its engine idempotency key is `process-next-operation-{instanceGuid:N}-{instanceVersion}`. The same instance/version intentionally collides regardless of action, task, or flow; actor/action/event differences remain in the engine-hashed request body and therefore produce an engine 409 rather than broadening deduplication. Dependent workflows retain `process-next-dependent-{workflowId:N}`.
- **A successful registered user action is followed by a full authoritative instance refresh.** `ProcessEngine` saves staged unit-of-work changes, then refetches the complete instance plus `Instance-Version` and `Process-State-Version`. Validation, form-data capture, signed callback state, enqueue identity, and acquire preconditions all use that same refreshed snapshot. This also covers action handlers such as signing that write Storage directly during the handler.
- **Commands run in separate HTTP requests** - each callback is independent; state is passed between commands via a signed, opaque JSON blob (see State Passthrough below)
- **Commands mutate in memory; the controller owns persistence.** Commands stage work on the `InstanceDataUnitOfWork`; the callback controller performs the workflow-owned Storage save (see Commit Boundary below)
- **Command phases**: initiating `AcquireProcessingStatus` → task-end/abandon commands → `MutateProcessState` (in-memory state transition) → task-start / process-end pre-commit commands → `CommitProcessState` (stages the process-state change and ownership decision; the controller save that commits it is the commit boundary) → `EnqueueSideEffectsWorkflow` (schedules the non-critical side-effect commands as separate `IsHead=false` single-step workflows, one per side effect, when the transition has any) → critical post-commit commands, including `ExecuteServiceTask` for a service-task target (see Command Sequences)
- **The callback `stepId` is required.** The engine sends its step database id as `AppCallbackPayload.StepId`; a callback without it is rejected as a bad request before any command runs, rather than defaulted to `Guid.Empty` (one key shared by every step of every instance). The controller forwards the id verbatim to Storage as the aggregate mutation's `Idempotency-Key` header, so the same id is greppable across the engine database, app logs, and Storage's idempotency records
- **Task-start reads get a clean slate.** `CleanupGeneratedFromTask` runs before the task-start hooks and removes elements generated by previous visits to the entering task (mirroring Storage's cleanup contract, but early enough that `OnTaskStartingHook`/`StartTask` never see stale data). An element referencing the entering task that is visible at task start was created by a retried attempt of the same transition.
- **`generatedFromTask` tagging is safe in any phase, including task start.** Storage's cleanup at `PutInstanceAndEvents` (stale data from previous visits - see altinn-storage#977 / app-lib-dotnet#1750) is timestamp-guarded: it only deletes elements created before the in-flight transition began, so elements created by task-start commands survive the save that completes their own transition. `SigningService` relies on this - signee states are created during task start tagged with the signing task. NOTE: the guard must exist in the Storage backend the app runs against (localtest has it; the altinn-storage PR must be deployed before this app-lib version is released).
- **Callback authentication** (see `Authentication/`): The app mints a JWT at enqueue time (signed with a `WorkflowEngineCallback` app-code, `jti` = instance guid, `secretId` claim identifies the code), carries it opaquely through the engine in `AppWorkflowContext.CallbackToken`, and the engine replays it on every callback in the `Authorization: Bearer` header. The callback controller authenticates with the `WorkflowEngineCallback` scheme (`WorkflowEngineCallbackAuthenticationHandler` in Altinn.App.Api); a selector policy scheme routes callback requests to it and all other requests to the default scheme, so the bearer token does not collide with platform auth. Validation checks signature, lifetime, and that `jti` matches the route instance. Data operations use `StorageAuthenticationMethod.ServiceOwner()`.
- **A workflow cannot outlive the app code that signed it, and nothing checks that it will not.** `WorkflowCallbackTokenGenerator` mints the callback token **once**, at the workflow's enqueue, with `Expires` set to the _signing code's_ `ExpiresAt` rather than to a lifetime of its own; the state blob that workflow carries is signed with the same code, and `WorkflowStateSigner` rejects it once the code expires. Neither is ever refreshed while it waits. Any workflow still waiting when its code expires therefore fails on the next callback: authentication runs first, so it is a **401**, which the engine host classifies as a client error (`AppCommand` treats every 4xx except 408/418/429 as a critical error) — so the step and its workflow go terminally `Failed` on the **first** attempt, with no retries and no backoff, and a resume replays the same stored token and fails the same way. This is a property of **long-running work in general, not of mailboxes**: an ordinary step deferring against the engine's `MaxStepWaitBudget` (14 days) and a mailbox receiver parked on `MaxMailboxTimeout` (21 days) fail identically, and neither is guarded. The exposure is bounded operationally rather than in code — the engine derives both maxima against the operator's app-code rotation policy, which leaves ≥114 days of remaining validity at enqueue against a worst case of 110 days (see the `MaxMailboxTimeout` xmldoc in `WorkflowEngine.Models/EngineSettings.cs` and `CallbackTokenLifetimeInvariantTests`).
- **State blob is signed independently of the token** (see `WorkflowStateSigner`): a leaked callback token cannot be combined with a forged/tampered state blob, because the blob carries a detached HMAC-SHA256 signature bound to a secret only the app holds. Signature/secret failures map to a non-retryable 422.

## Command Sequences

Defined in `WorkflowCommandSet.cs`; `ProcessNextRequestFactory.AssembleCommandSequence` assembles the sequences:

1. `AcquireProcessingStatus` for a chain-initiating workflow; never for an engine-owned dependent workflow
2. Task-end/abandon commands (from `process_EndTask`/`process_AbandonTask` events)
3. `MutateProcessState` (inserted by the factory if there are task-end/abandon commands)
4. Task-start and process-end commands (from `process_StartTask`/`process_EndEvent` events)
5. `CommitProcessState` (always inserted by the factory) — stages the `ProcessStateChange` and
   processing-status keep/clear; the controller save commits it
6. `EnqueueSideEffectsWorkflow` (inserted by the factory when the transition has side-effect
   commands) — enqueues the **side-effects workflow**
7. Critical post-commit commands (`CriticalPostCommitCommands`) — must complete before the
   transition settles; they run after the controller save for `CommitProcessState` has committed

`CreateChainInitiating` and `CreateDependent` are deliberately separate factory entry points. Initial process start and user-triggered process-next use the former, so acquire is command index 0 with no earlier side effect. `ExecuteServiceTask` auto-advance uses the latter with the existing dependency and idempotency key; dependent workflows inherit `processing` and do not reacquire it.

All of the above form the **Main workflow** — the only workflow in the enqueue batch. The
non-critical side-effect commands (`SideEffectCommands`) travel inside step 6's payload as a
pre-assembled enqueue request; when that step executes — immediately after the commit — it submits
them to the engine as separate **side-effects workflows, one single-step workflow per side effect**,
in one atomic batch. Each sibling is an independent root (`DependsOn = null`,
`DependsOnHeads = false`), invisible to the collection heads frontier (`IsHead = false`), carrying
the commit-time state blob as its own state (see State Passthrough), `links`-related to the Main
workflow, with an OperationId prefixed `Process next side-effects:` and suffixed with its command
key (e.g. `Process next side-effects: Task_1 -> Task_2 · MovedToAltinnEvent`). The batch enqueue is
idempotent per Main workflow (one idempotency key, `{mainWorkflowId}:side-effects`, covering the
whole batch — the engine's batch enqueue is atomic), so step retries dedup. Because the step runs
inside Main before it settles, the side effects exist **if and only if** the transition committed —
a pre-commit failure schedules nothing, and a committed transition's side effects run independently
of whatever happens to Main afterwards (post-commit failure, reject/abandon). The ProcessNext wait
and the next transition key off Main only: a slow or failing event registration can never gate the
API response or wedge the instance's process pipeline, and the side effects start at the commit
rather than after e.g. a service task. One workflow per effect means the effects also fail
independently of _each other_: a dead-lettered event registration cannot starve the notification
behind it, each effect gets its own retry pacing and redrive, and a failed workflow is named for
the one effect it carries. When there are no side-effect commands, a single workflow without the
enqueue step is emitted — identical to the pre-split behavior.

**Ordering is not guaranteed between side effects at all** — neither across transitions nor between
effects of the same transition (each rides its own workflow): a retrying `movedTo.Task_2`
registration can land after `movedTo.Task_3` (or after `completed`). This matches the platform: the
Altinn Events service itself delivers at-least-once and unordered (competing consumers, no Service
Bus sessions, and per-event retry parking up to 12h — see the ordering section of the ADR), so
ordered registration was never observable by subscribers. Consumers that mirror process state from
Altinn events must tolerate out-of-order (and duplicate) delivery. Should a side effect ever
genuinely need to run after another, express it with an explicit `DependsOn` between the siblings —
never by step order.

Post-commit categorization: `ExecuteServiceTask` is **critical** (stays in Main);
`MovedToAltinnEvent`, `InstanceCreatedAltinnEvent`, `CompletedAltinnEvent`, and
`NotifyInstanceOwnerOnInstantiation` are **side effects**. (`EndProcessLegacyHook` runs pre-commit,
and the configured process-end cleanup/hard delete is staged by `CommitProcessState` into the
commit save itself.)

### Task-to-Task Transition (e.g., Task_1 → Task_2)

```text
Main workflow:
AcquireProcessingStatus (idle → processing)
── instance.Process.CurrentTask = Task_1 (OLD) ──
EndTask → CommonTaskFinalization → OnTaskEndingHook → LockTaskData
  ── MutateProcessState (in-memory: CurrentTask → Task_2) ──
── instance.Process.CurrentTask = Task_2 (NEW) ──
UnlockTaskData → CleanupGeneratedFromTask → OnTaskStartingHook → CommonTaskInitialization → StartTask
  ── CommitProcessState (stages process state; controller save commits it) ──
EnqueueSideEffectsWorkflow → [ExecuteServiceTask if the target is a service task — one engine step per
                              pipeline stage, then the concluding one; or, if the pipeline opens a mailbox,
                              MintMailbox immediately before the declaring stage and then that stage, which
                              ends Main. Main's last step carries nothing about what follows it: it derives
                              that when it runs, from the item composed after its own]

Side-effects workflow (single-step independent root, IsHead=false, own commit-time state, links→Main):
MovedToAltinnEvent

Mailbox receive workflow (only for a mailbox pipeline; single-step head depending on the current head,
own mailbox declaration, fresh callback token): the handler that answers that exchange, alone — by its
item index. A reply handler is never anything but a workflow of its own.

Mailbox continuation workflow (a head depending on the current head, no mailbox declaration, fresh
callback token): the pipeline's next segment — everything up to and including its own next
mailbox-opening stage, or up to (excluding) the next reply handler, or the concluding step
```

### Task-to-End Transition (e.g., Task_1 → EndEvent)

```text
Main workflow:
AcquireProcessingStatus (idle → processing)
── instance.Process.CurrentTask = Task_1 (OLD) ──
EndTask → CommonTaskFinalization → OnTaskEndingHook → LockTaskData
  ── MutateProcessState (in-memory: CurrentTask → null, EndEvent set) ──
OnProcessEndingHook → EndProcessLegacyHook
  ── CommitProcessState (stages ended state/events + processing → idle +
                         configured element cleanup + optional hard delete in one save) ──
EnqueueSideEffectsWorkflow

Side-effects workflow (single-step independent root, IsHead=false, own commit-time state, links→Main):
CompletedAltinnEvent
```

Process-end cleanup is part of the `CommitProcessState` aggregate. `CommitProcessState` accepts only an active shape (`Ended` null and `CurrentTask` present) or a terminal shape (`Ended` present, `CurrentTask` null, and `EndEvent` nonblank); every other shape fails before any process/status/cleanup/deletion staging. Configured elements are staged for deletion in the same save; an in-aggregate unlock is staged first so locked task data is emitted with `ignoreLock=true`. Optional hard deletion is also part of that exact terminal aggregate. There is no version-bumping Storage callback after the clearing/hard-delete commit.
`EndProcessLegacyHook` deliberately runs before the terminal commit, after the ended state is installed in memory, so public app `IProcessEnd` implementations can inspect `EndEvent` and pre-cleanup data while `processing` still blocks unsupported direct Storage mutations. `CompletedAltinnEvent` remains after the commit; it only publishes through `IEventsClient.AddEvent` and does not perform an instance-version/process-version save.

### Initial Task Start (process just created)

```text
Main workflow:
AcquireProcessingStatus (idle → processing)
── instance.Process.CurrentTask = Task_1 (already set by CreateInitialProcessState) ──
UnlockTaskData → CleanupGeneratedFromTask → OnTaskStartingHook → CommonTaskInitialization → StartTask
  ── CommitProcessState (stages process state; controller save commits it) ──
EnqueueSideEffectsWorkflow → [ExecuteServiceTask if service task — one engine step per pipeline stage, then the concluding one]

Side-effects workflows (one single-step independent root per effect, IsHead=false, own commit-time state, links→Main):
MovedToAltinnEvent ∥ [InstanceCreatedAltinnEvent if instantiation] ∥ [NotifyInstanceOwnerOnInstantiation if configured]
```

### Task Abandon (reject → end)

```text
Main workflow:
AcquireProcessingStatus (idle → processing)
── instance.Process.CurrentTask = Task_1 (OLD) ──
AbandonTask → OnTaskAbandonHook
  ── MutateProcessState (in-memory: CurrentTask → null or next task) ──
[OnProcessEndingHook if ending] / [task-start commands if moving to next task]
  ── CommitProcessState (stages process state; controller save commits it) ──
[EnqueueSideEffectsWorkflow if the target emits side effects] → [critical post-commit commands]

Side-effects workflows (only when the target emits side effects, one per effect):
[side-effect commands]
```

### Side-effect failure observability and redrive

Side-effect failures never gate anything and never surface in the ProcessNext result **or** the
read-path `workflow` status annotation: a failing event registration retries per the engine's step
retry strategy (production default: exponential backoff up to 24h `MaxDuration`) and then lands as
a terminal `Failed` workflow that nothing waits on and no user ever sees. A terminally failed
side-effects workflow means outbound events/notifications were **lost** — downstream event
subscribers never learn of the transition — so this class must be monitored explicitly:

- **Alert** on the engine metric `engine.workflows.execution.failed` with `reason` in
  (`execution`, `poisoned`) across **all** `is_head` values — every terminal failure needs ops.
  There is no user-facing Retry for terminally failed workflows (the failed screen shows error
  details + contact support; the frontend recovers on its own once the workflow is resumed), so
  an ops resume is the only recovery path. Use `is_head` to route/prioritize, not to filter:
  `is_head="false"` means a side-effects workflow failed — outbound events were lost, re-deliver
  via the engine resume; `is_head="unset"` (or `"true"`) means a head (Main) workflow failed — the
  instance is stuck for the user until ops resumes it (cascade) via `process/resume`. Do **not**
  alert on `reason="dependency_failed"`: a side-effects workflow has no dependencies and never
  lands there; the increments come from dependent Main workflows (auto-advance chains) condemned by
  an upstream Main failure that already fired the alert, and the cascade resume of that failure
  revives them.
- **Enumerate** with `GET /api/v1/{org}/{app}/workflows?status=Failed` — side-effects workflows are
  identifiable by `isHead: false` on the status response (their OperationId also carries the
  human-readable `Process next side-effects:` naming prefix and names the one effect it carries,
  e.g. `… · MovedToAltinnEvent`), or scope to one instance by
  `collectionKey`/`processNextInstanceGuid` label.
- **Redrive**: resume the failed workflow via the engine's resume API — a resumed side-effects
  workflow re-runs its remaining steps and re-delivers its events (event registration is
  idempotent per event). A side-effects workflow exists only for a **committed** transition and
  carries its own commit-time state, so a redrive is always valid — there is no
  "correctly dead" case to distinguish. Note that the app's `POST process/resume` deliberately
  does **not** touch side-effects workflows (they are excluded from the resume-target lookup); the
  engine-level resume is the only re-emit path. The Main workflow it belongs to is reachable via
  the workflow's `links`. The redrive window is implicitly bounded by the engine's
  terminal-workflow retention sweep (default 60 days): after that the failed workflow — including
  the state a resume would need — is purged.

### Task-Start Cleanup Ordering

Task-generated-data cleanup lives in `CleanupGeneratedFromTask`, which runs right after `UnlockTaskData` and before `OnTaskStartingHook`, so all task-start logic (including app-supplied hooks) reads a clean slate. The unlock runs first because elements generated by a previous visit may still be locked from that visit's `LockTaskData`. The full task-start ordering is pinned by `ProcessEngineTest` and `ProcessNextRequestFactoryTests`.

## Commit Boundary and Empty Saves

`CommitProcessState` is the commit boundary in the workflow sequence, but it does not write to Storage itself. It validates and stages the `ProcessStateChange` on the `InstanceDataUnitOfWork`; the controller's workflow-owned save (`SaveWorkflowOwnedAggregate`) in that same callback commits that process-state mutation. Other callbacks use the same controller-owned workflow save for their own data changes, pending lock statuses, and derived instance-field updates.

`AcquireProcessingStatus` stages exactly expected `idle` → new `processing` and updates the in-memory snapshot before it is re-signed; because the status lives inside the process payload, its save also sends a full `processState` update synthesized from that snapshot. Every subsequent workflow-owned save defaults to expected `processing`. `CommitProcessState` normally stages expected `processing` → new `idle`. When the exact sequence constructed by the factory contains a following service-task command, the factory sets `ServiceTaskFollows` in the private commit payload and the commit instead keeps `processing`. This indicator is produced by the same `WorkflowCommandSet` branch that appends `ExecuteServiceTask`; it is not a task-type classifier, app-facing option, hidden global, or signed runtime continuation result.

The target service task is therefore durable before its side effects run. `ExecuteServiceTask` keeps `processing` only for the known `ServiceTaskSuccessResult` auto-advance branch and returns its exact action. Explicit failure results clear/enqueue nothing. Every other runtime result—including known no-auto success, an app-defined `ServiceTaskResult` subtype, or legacy null—pauses at the durable service task, stages expected `processing` → new `idle`, and returns no auto-advance. The controller saves any service-task data/status mutation and captures updated state before enqueueing the dependent workflow with an auto result's action. A service-task failure leaves Storage at the target service task plus `processing`, so resuming the existing workflow retries `ExecuteServiceTask` without reacquiring. The dependent workflow does not acquire and its final commit clears to `idle`.

All Storage-visible mutations in workflow callbacks must be staged through `InstanceDataUnitOfWork` and persisted by the controller's standard save path. Direct `IDataClient`/`IInstanceClient` writes from commands or app hooks are unsupported; while ownership is `processing`, Storage rejects ordinary mutation paths that do not supply the workflow aggregate's expected status. Do not add a separate pre-enqueue acquire call or a command-owned Storage save.

Between `MutateProcessState` and `CommitProcessState`, the callback snapshot can intentionally be ahead of Storage. A workflow-owned data-only aggregate response refreshes authoritative data, versions, instance fields, and process `Status`, but retains the in-memory process shape for the next signed callback; the same rule applies after replay reconstruction. A save that carries a process payload — a staged process state, or the update synthesized for a status-only transition — uses Storage's returned process snapshot instead.

The controller skips Storage when the aggregate mutation plan is empty. The skip is retry-safe because it is deterministic: the same input state blob rebuilds the same unit of work, the command creates the same plan, and the controller reaches the same save-or-skip decision. An otherwise empty command can still save intentionally when the full mutation plan contains derived `dataValues` or `presentationTexts` updates.

## Replay Semantics

Storage's aggregate mutation endpoint admits replay by `(instance, previous instance version, idempotency key)`. On replay it returns the original response without reading the request body. This is required because retried callbacks may regenerate different bytes or JSON ordering while still representing the same already-committed workflow step.

When Storage marks the mutation response as replayed, `InstanceDataUnitOfWork` does not remap created data element ids onto the current attempt's local changes. Instead it rebuilds from Storage's authoritative state, clears local caches and tracked changes, refreshes version and ETag metadata, and throws `InstanceMutationReplayedException`.

`WorkflowEngineCallbackController` is the caller that handles this exception. It logs at information level and continues to capture state from the rebuilt unit of work. The semantic is first-commit-wins: the workflow proceeds with the result committed by the first successful attempt. Any other caller that receives `InstanceMutationReplayedException` fails permanently, because a retry with the same key would deterministically replay again.

## Waiting, Failure Classification, and Reject/Resume

`WorkflowEngineService` does more than fire-and-forget. After enqueueing it polls the workflow **collection** (keyed by the instance guid — every transition of an instance shares one collection) until the active heads settle, then refetches the instance and builds a `ProcessNextWorkflowResult`:

- **A parked chain releases early.** When every active workflow in the anchored chain is `Waiting` (a service task deferred), the wait releases with the ordinary success shape after a short grace window (~2s, so near-instant polls still complete synchronously). Deferral is post-commit by construction (only `ExecuteServiceTask` defers, after `SaveProcessStateToStorage`), so the instance already carries the committed target task; the read-path `workflow` annotation and the frontend waiting UI take over from there. A committed-state guard makes a hypothetical pre-commit deferral fall through to the ordinary timeout instead. The 100s timeout (504/`Timeout`) is thereby reserved for chains that are genuinely slow or stuck.

- `ScopeToCurrentChain` narrows the collection to the workflow just submitted and everything created after it, so lingering terminal heads from earlier transitions don't leak into the current wait. It also strips side-effects workflows (matched by the engine-persisted `isHead == false` head-visibility directive; the `Process next side-effects:` OperationId prefix is a naming convention only) from every path: they must not extend the wait — they are enqueued mid-Main, so they are strictly newer than the anchor and would otherwise leak into the chain — and their failures must never be classified as transition failures.
- `BuildWorkflowFailure` classifies the outcome into a `WorkflowFailure` (`AcquireConflict`, `StepFailed`, `DependencyFailed`, `EngineFault`, `Timeout`, or a superseding-abandon case). `AcquireConflict` is reserved for a non-retryable `AcquireProcessingStatus` failure carrying the callback's structured concurrency code while acquire is the first command. At the Storage boundary, a 409 receives that code only when its ProblemDetails `type` is exactly `process_status_conflict`; unrelated aggregate-mutation 409s remain ordinary resumable failures. The waiting path abandons the side-effect-free acquire conflict before returning HTTP 409, releasing its stale enqueue idempotency key and preventing `resumeRequired`. An abandon compare-and-set loss is re-polled and reclassified, but every such path remains bounded by the same internal polling deadline. A failure after acquire is never written off and remains resumable. `ExtractCallbackErrorDetail` unwraps the ProblemDetails `detail` from an engine error message so the human-readable reason is available server-side (logged by the controller); the raw message is never serialized to clients — failed action responses ship a stable generic `detail` plus a `workflowFailure` stripped of its recorded error.
- `HasCommittedProcessState` reports whether `CommitProcessState` completed, so the caller knows if the transition was persisted even when a later step failed.

`GetCurrentTaskWorkflowState` returns a closed set — `Unblocked`, `Retrying(workflowId, collectionKey)`, or `ResumeRequired(workflowId, collectionKey)` — used before enqueueing a new action so a still-running or terminally-failed transition blocks the next action.

`ResolveWorkflowTaskStatus` is its read-path sibling: a presentation projection (idle / processing / failed + target task + failure kind, plus the failed workflow id/timestamp as a support reference) used by `ProcessStateEnricher` to annotate every process/instance read. A transition parked on a deferring service task additionally carries `waitingReason` — the task's own words from its most recent `Defer`, passed through from the engine's collection-head view — so a waiting UI can say what is being waited for. The frontend renders a terminal failure as an error page carrying that support reference — deliberately **no user Retry** (the engine already exhausted its retry budget) and no polling (the failed page is static — a terminal failure needs manual intervention either way); recovery is ops calling `POST process/resume` followed by the user refreshing the page. **Known gap:** for an ended process (`CurrentTask == null`) it reports idle without consulting the engine, so a terminal failure in the final transition's post-commit steps (which run after `ended` commits) never surfaces on a read — detection is ops alerting on the engine's failed workflows.

Reject/resume/abandon:

- `ResumeAndWaitForWorkflow` resumes a failed workflow (cascade) and waits for it to settle — sharing the wait above, so a resumed workflow that immediately defers again also releases early with the waiting UI.
- `AbandonWorkflow` writes off a terminally failed workflow (`Failed → Abandoned`) so a subsequently enqueued workflow can depend on it; returns `false` if the engine's compare-and-set was rejected (e.g. a concurrent resume revived it).
- `EnqueueDependentProcessNext` enqueues a workflow that `dependsOn` another (used by the reject flow to supersede a failed transition, and by auto-advance).

## State Passthrough

Each callback needs the app's workflow callback state (`instance` + storage versions + `formData`). Rather than fetching from Storage on every callback (which would see stale process state), the app captures that state into a **signed** opaque string that the engine stores and echoes back with each callback. The instance snapshot includes `Process.Status`, so acquire/keep/clear survives callback restore and recapture.

**Signing**: `WorkflowStateSigner.Sign` wraps the serialized `WorkflowCallbackState` in a `SignedWorkflowState` envelope with a detached HMAC-SHA256 signature and the `secretId` of the signing code. Every `Sign`/`Verify` names a `SigningDomain` (see `SigningPurpose`), and the state blob's is `CallbackState`, which is **underived** — signed with the app-code directly, so blobs signed before domains existed still verify. That is pinned by known-answer vectors in `WorkflowStateSignerTests` rather than by round-trips, which would agree with themselves after any change. `Verify` re-computes the signature (constant-time compare), rejecting tampering, unknown/expired secrets, and malformed envelopes — all mapped to a non-retryable 422. The blob's signing lifetime tracks the callback token's (same clock skew), so blob and token fail together during code rotation.

**Flow**:

1. `WorkflowCallbackStateService.CaptureState` → serializes instance + form data (+ the carry's contents) into `WorkflowCallbackState`, then signs it → string
2. The signed string is included in `WorkflowRequest.State`
3. Engine echoes it back in `AppCallbackPayload.State` for each callback
4. `WorkflowCallbackStateService.RestoreState` → verifies the signature, deserializes, asserts the blob's instance matches the callback route instance, then returns an `InstanceDataUnitOfWork` with preloaded form data plus the `WorkflowCallbackStateCarry` the blob was holding
5. After command execution and the controller save/replay handling, the updated state — data _and_ carry — is captured, re-signed, and returned in `AppCallbackResponse.State`
6. Engine uses the returned state for the next callback — state evolves command by command. For a **deferred** step the app echoes the incoming state back unchanged (deferral is stateless — the controller rejects a deferring handler that made data changes), and the engine hands a deferred step its own returned state on the next attempt (`ResolveStateIn` prefers a step's own `StateOut`), so every re-check starts from exactly the state the step first received.

**Capture point**: after a registered user action succeeds, `ProcessEngine` first refetches the complete authoritative Storage snapshot and both versions. It then captures state BEFORE the in-memory process state is mutated to the next task. The blob carries the OLD process state (CurrentTask = the task being left) and exactly the versions used in the chain-initiating enqueue key/acquire fence. `MutateProcessState` transitions the in-memory state to the new task between the two command groups.

**Side-effects workflow state**: the side-effects workflow carries the **commit-time state blob** as its own `State`. `EnqueueSideEffectsWorkflow` runs immediately after the controller save for `CommitProcessState` has committed, so its `StateIn` — the blob it forwards — is exactly the state the transition committed: the (NEW) process state plus every data change made up to the commit. Side-effect commands therefore always act on committed data, even when the transition ended the process and the instance was auto-deleted from Storage. (They do not see changes made by _later_ critical post-commit commands such as `ExecuteServiceTask` — the events describe the commit, not what happened after it.)

**Why commands read from `instance.Process.CurrentTask`**: In the old ProcessEngine, task-end/start handlers received `taskId` as an explicit parameter. The new commands read directly from `instance.Process.CurrentTask` — single source of truth. `MutateProcessState` ensures each command group sees the correct CurrentTask.

## How to Add a New Command

1. **Create the command class** in the appropriate `Commands/` subfolder:
    - Without payload: implement `IWorkflowEngineCommand` directly
    - With typed payload: extend `WorkflowEngineCommandBase<TPayload>` and create a `record TPayload : CommandRequestPayload`

2. **If using a payload**: register it in `CommandPayload.cs`:
    - Add `[JsonDerivedType(typeof(MyPayload), typeDiscriminator: "myPayload")]` to `CommandRequestPayload`
    - Add `[JsonSerializable(typeof(MyPayload))]` to `CommandPayloadJsonContext`
    - Payload serialization emits `$type`; `CommitProcessState` uses the `processStateChange` discriminator

3. **Register in DI**: add `services.AddTransient<IWorkflowEngineCommand, MyCommand>()` in `ServiceCollectionExtensions.cs`

4. **Add to sequence**: add to the appropriate method in `WorkflowCommandSet.cs` (use `AddCommand` for pre-commit, `AddCriticalPostCommitCommand` for post-commit work the transition must wait on, `AddSideEffectCommand` for fire-and-forget post-commit work that runs as its own non-gating single-step side-effects workflow). Side-effect commands see the commit-time state (the exact state the `CommitProcessState` controller save persisted) — but remember the only timing guarantee is that they never gate the transition: they are independent roots the engine may start as soon as they are enqueued at commit, possibly before the process-next response is sent, in parallel with Main's critical post-commit commands _and with each other_, and they must stay idempotent and non-blocking.

5. **Startup validation**: `WorkflowEngineCommandValidator.Validate` will fail at startup if a key in `WorkflowCommandSet` isn't registered in DI

## Command Conventions

- Every command has `public static string Key => "..."` and `public string GetKey() => Key`
- Commands return `SuccessfulProcessEngineCommandResult`, `DeferredProcessEngineCommandResult` or `FailedProcessEngineCommandResult` (never throw from Execute). `FailedProcessEngineCommandResult` distinguishes `Retryable` (→ 500, engine retries) from `Permanent`/`NonRetryable` (→ 422, engine gives up). `DeferredProcessEngineCommandResult` is neither: it returns 200 with a `defer` block, so the engine parks the workflow in `Waiting` and re-executes the step later — no error recorded, retry counter reset. A deferring step keeps processing ownership: it has not concluded, and releasing it would mean staging a mutation, which a stateless deferral must not do. Today only `ExecuteServiceTask` produces one (from `ServiceTaskResult.Defer`); the app-facing contract, the wait budget (`ProcessStepOptions.WaitBudget`) and the two clock groups a task reads to pace itself (`context.Attempt` for this execution, `context.Wait` — incl. the derived `Remaining`/`IsFinalCheck` — for the whole wait) are documented in the authoring guide, `docs/service-task-pipelines.md` at the backend root. For send-then-poll (or any multi-phase) tasks: implement `IPipelineServiceTask`, give each earlier phase its own stage and let `Finally` conclude — the engine's step ledger is the durable send guard (a completed stage never re-runs; a retry or resume re-enters at the failed stage), never anything under `Attempt`/`Wait`; `StepId` (per stage) is the outbound idempotency key covering the in-attempt crash window (see the authoring guide). `EFormidlingServiceTask` is the worked example in-tree: a send stage, a polling `Finally` that owns the wait budget, a backoff ladder driven by `Wait.DeferCount`, and a `FailedPermanent` on `Wait.IsFinalCheck` that names what never arrived instead of expiring generically, and a `PlatformHttpException` with a 4xx status (other than 408/429) mapped to `FailedPermanent` in both stages — the integrasjonspunkt's verdict on the request would otherwise ride the engine's default retry strategy as a 500 for a day
- **Pipeline service tasks**: every service task IS a pipeline — `IPipelineServiceTask` is the root contract (`Define(builder)` composes `Stage(work, options?)*` and `HandleReplies(handle, …)*`, in any order, + exactly one terminal — `Finally(work, options?)` or `ConcludeOnReplies(handle, …)`, either of which is legal for a pipeline that opened mailboxes so long as every one of them is answered; the builder's types make any other shape uncompilable), and `IServiceTask` derives from it with a **sealed forwarding default**: `Define => pipeline.Finally(Execute)`. The runtime therefore has exactly one dispatch path (resolve pipeline via `ServiceTaskLookupExtensions.ResolvePipeline`, then dispatch on the **one item index the step carries** — a position in `ServiceTaskPipeline.Items`, naming the one item that step runs), and the simple task's concluding-step semantics are a derived fact, not a special case. **The conclusion is an ordinary `PipelineItem`**, appended last by the only `ServiceTaskPipeline` constructor, so "exactly one conclusion, and it is last" is structural rather than validated — `Items` is the whole pipeline in one list, read by shape and indexed by position, with no `Conclusion` property held apart from it for a consumer to have to remember. The factory expands one `ExecuteServiceTask` engine step per **stage** at enqueue time, and one for the conclusion when it is a `FinalStep` — a reply handler's `ExecuteServiceTask` step is the whole of a *receive workflow* instead and never shares a workflow with anything, so a `ReplySegment` or a `ReplyExchange` conclusion contributes no step to the segment it ends; that segment ends with its **last stage's step**, whose completion is what enqueues the exchange's first receiver, worked out when that step runs (see Mailboxes below). Every step it does emit carries the index of the item it runs (payload carries that index; OperationId is `ExecuteServiceTask: {index}` **without exception — stages, reply handlers and the conclusion alike**, so a simple `IServiceTask`'s one step reads `ExecuteServiceTask: 0` and a bare `ExecuteServiceTask` OperationId is constructed nowhere under `src/`) — for an `IServiceTask` that concluding step is the whole expansion. "No index" is not a meaning this expansion has left to give: it was the old conclusion convention, and retiring it is what makes every step's identity one comparable thing. (That is Main's whole expansion only for a pipeline that opens no mailbox: a declaring pipeline's Main carries its **first segment** — which ends at the first mailbox-opening stage, inclusive, or before the first reply handler — and its later segments ride the workflows each preceding segment's last step enqueues, see Mailboxes below.) The index travels **three ways** on every such step, deliberately: in the payload, which dispatch reads; in `StepRequest.ServiceTaskItemIndex`, which the enqueueing hop resolves the step's options by (reading it back out of the payload would mean deserializing what that hop just wrote); and in the OperationId, which is the engine's own record of the step. The expansion fixes the pipeline's shape for the workflow's lifetime — an item is identified by its **position**, so reshaping the composition mid-flight (stages or reply handlers inserted, reordered or removed) shifts every index behind it and can strand in-flight callbacks with permanent `PipelineItemNotFound`. That hazard is deliberately **unguarded**, because it was never specific to identity: naming a stage never guaranteed in-flight compatibility — a redeploy can keep every name and still break an old enqueue with changed stage semantics or data contracts — and *any* mid-flight change to the composed process invalidates an old enqueue exactly as an edited BPMN file does. It is the general versioning problem the app developer owns; nothing here trips a wire on it. Stages share state through the ordinary mechanism only: a completed stage's data changes are saved into the state blob the engine hands the next stage — no separate handoff channel, and a deferring attempt saves nothing. Options: a step's own builder options — a stage's from `Stage`, a mid-pipeline reply handler's from its own `HandleReplies`, the conclusion's from whichever terminal ended the chain — win field-wise over the task's own, which are the fallback for every step. **The three sources are alternatives, never a chain**: whatever one step leaves unset falls back to the task's options and never to another step's, so a `HandleReplies` declaring only a timeout does not inherit the terminal's wait budget — that budget belongs to a different exchange. (Hence `ProcessStepOptionsResolver` needs no branch **among the three sources**: one lookup, `pipeline.Items.ElementAtOrDefault(itemIndex)?.StepOptions`, merged field-wise with the task's own — the only test left is whether the step names an item at all, which a `MintMailbox` step does not. One item, one fallback: the property is the shape of the lookup rather than a rule enforced on top of it.) Declare a polling pipeline's wait budget on `Finally`, since a budget on the task also reaches stages that never wait. Registration: `AddTransient<IServiceTask, …>` or `AddTransient<IPipelineServiceTask, …>` per the implemented interface (the type system forbids the wrong pairing; lookups union both). `ServiceTaskRegistrationValidator` fails startup on a throwing/null `Define` (the builder rejects bad options, a handle from another pipeline or answered twice, and a mailbox left unanswered when a terminal ends the composition — all eagerly, from the composing call itself; "answered twice" and "left unanswered" also have compile-time front-ends in analyzer rules `ALTINNAPP0702`/`ALTINNAPP0703`, which report only what is provable of one `out MailboxHandle` local — two answers in one branch-free run of the method that every returning execution goes through, and a handle never mentioned again — and leave every other shape, the foreign handle included, to these throws) and on an `IServiceTask` replacing the sealed `Define` (backstop for analyzer rule `ALTINNAPP0700`). `Define` must be cheap/deterministic/side-effect free — it runs at enqueue, on every callback, and at startup. Gotcha: Moq mocks bypass the forwarding default (null pipeline → legible failure); use real fakes in tests
- Commands get instance data through `context.InstanceDataMutator`, typed as `IInstanceDataMutator`. Task data lock/unlock commands deliberately assert that the runtime object is `InstanceDataUnitOfWork`, because data-type lock mutation is workflow-owned and is not part of the app-facing mutator surface
- Commands pass `context.CancellationToken` into app-facing contexts (`ProcessTaskContext`, hook contexts, and `ServiceTaskContext`)
- Commands do not persist directly. They stage work on the unit of work; the callback controller performs the workflow-owned save after successful execution
- Hook commands (`OnTaskStarting`, `OnTaskEnding`, `OnTaskAbandon`, `OnProcessEnding`) enforce max 1 handler per task
- Each service task gets one `ExecuteServiceTask` callback after `CommitProcessState` has durably installed the target task with `processing`. `ServiceTaskContext.IdempotencyKey` is the retry-stable workflow step database id from the callback payload (`AppCallbackPayload.StepId`); the required `ExecutionReferenceTime` is `Workflow.StartAt ?? Step.CreatedAt`. The engine reuses both values on retries of that persisted step.
- `CommitProcessState` keeps `processing` from the factory-known fact that a service-task command follows. `ExecuteServiceTask` then clears for a paused result or returns the exact auto-advance action while keeping `processing`; the callback controller saves staged service data/status before enqueueing the dependent process-next workflow

### Mailboxes

- **Declaring one — the composition surface.** A pipeline answered by a message rather than by polling opens one from the stage that sends: `pipeline.Stage(SendIt, new MailboxOptions { Timeout = … }, out MailboxHandle handle)`, answered by exactly one handler: `HandleReplies(handle, onMessage, onClosed)` for an exchange the pipeline carries on past, or `ConcludeOnReplies(handle, onMessage, onClosed)` for the one it ends on. The declaration is a **`Stage` overload**, not a modifier on the composed pipeline: the declaration and the mailbox-aware delegate must travel together (a modifier applied after the fact cannot retype an already-supplied delegate), and an overload has no "modifier with no stage to attach to" error path to guard in the first place. Internally the stage is a `ServiceTaskStage.MailboxOpening` holding the `MailboxOptions` as its `Declaration`; `ServiceTaskStage` is a closed two-member hierarchy (`Plain` / `MailboxOpening`), so each shape's work delegate takes exactly the arguments it needs and no execution reads a nullable declaration to rediscover which kind of stage it is running. The `MailboxHandle` the overload hands out is opaque and impossible to construct, which makes "a reply handler answers a really-declared mailbox" a **compile-time** fact rather than something resolved by a runtime lookup; the builder adds only what types cannot say — the handle belongs to this builder, it is answered exactly once, and **every terminal, `Finally` as much as `ConcludeOnReplies`, refuses outright if any mailbox other than the one it answers is still unanswered**, naming the index of the stage that opened it. A terminal *is* the end of the composition, so a mailbox still waiting for its handler there is waiting for a call that will never be made; a mailbox already answered by `HandleReplies` is no obstacle to either terminal, since that answer is one of the pipeline's own items and travels with it. (One case reads oddly and is deliberate: a mailbox answered by an *earlier* `ConcludeOnReplies` still fails a later terminal, because a terminal's answer is the conclusion of the one pipeline that terminal returned — two terminals on one builder are two pipelines, and the one left behind takes its exchange's answer with it. The message says so rather than telling the author to answer what they just answered.) All eager, so a mistake is an app startup failure rather than a callback failure days later. Nothing guards a discarded return any more: a terminal is the only way to obtain the `ServiceTaskPipeline` that `Define` must return, so no return value can be discarded to lose a declaration. That is why `ServiceTaskPipelineBuilder`'s constructor is `internal`: with a public one, a `Define` could compose on a builder of its own and return that pipeline, spreading one composition over two builders — a declaration made on the builder it did not return from is dropped silently, with no eager throw and no mint step, precisely the case the deleted `ResolvePipeline` check covered. The runtime being the only source of a builder closes that, and `Altinn.App.Core.Tests` composes one directly only because it is an `InternalsVisibleTo` friend. **One builder type, no intermediate chain types, handles rather than a mailbox-flavored builder** is a settled decision rather than an oversight: a second builder returned by the overload would make most of those eager checks structural instead, but multi-exchange needs handles to say *which* exchange each handler answers, so a handle-free first cut would only have had to reintroduce them later — which is exactly what happened next. **A task may open several mailboxes, and they are processed strictly sequentially in *handler* composition order** — one relay chain: Main → exchange A's receivers → continuation → exchange B's receivers → … → the terminal's conclusion → process-next, with one continuation hop per *send* as well, since an opening stage ends its own workflow (so up-front sends read Main → continuation → exchange A's receivers → …). Three properties follow, and the composition surface is where the author decides all three. **Handler order is exchange order, not send order:** `Stage(A) → Stage(B) → HandleReplies(A) → ConcludeOnReplies(B)` sends both messages up front and still reads A's exchange to the end before B's begins, and `HandleReplies(B)` before `HandleReplies(A)` is equally legal when both stages precede both handlers — nothing validates ordering beyond what handles make structural (a handler can only name an already-composed stage). **A later exchange's messages wait in its log until the chain reaches its handler** — head-of-line blocking, **by design** rather than a gap: it is the price of the linear chain every invariant here rides on, and it costs no messages, because the engine births a receiver holding its waiting message even after the mailbox closed, so an exchange that expired while an earlier one ran still drains its backlog before its closing signal surfaces. **Each deadline runs from its own send**, since the mint step hugs its stage wherever that stage rides: a send composed *before* a handler spends its own exchange's budget while the earlier exchange runs, while a send composed *after* one starts its clock only when the earlier exchange concludes — so up-front sends buy overlapping clocks, later sends buy undiminished budgets, and stage placement is the whole lever. Up-front clocks start one engine hop apart rather than within one workflow, since each opening stage rides a segment of its own; the ordering the author chose is unaffected, and no exchange's budget is diminished by the send before it. Still not on offer: **concurrent** exchanges with a join semantic, and **interleaving** — one handle answered by two handlers, yield/resume style — which the model deliberately does not preclude but does not provide either. Two exchanges that must genuinely overlap are still two BPMN tasks.
- **The mint is its own engine step**, `MintMailbox` (OperationId `MintMailbox: {index}`), emitted immediately before its declaring stage. Its position is load-bearing in both directions: the deadline clock starts at the mint, so no earlier stage may erode the exchange's budget, and the stage must never send without an address, so nothing may mint after it. What its position rules out is an earlier *stage* spending that budget; an earlier *exchange* spends it whenever its send was composed up front, which is the author's choice and the stage-placement decision the composition surface describes above. A step of its own rather than part of the stage's execution because the mint's outcome is durable and the stage's is not — the mint completes once and never re-runs, while the stage after it may fail, defer and re-run against the address already published. It mints via `POST {engine}/{ns}/mailboxes` keyed on **its own** `StepId` (the step id the engine sent it on that callback — pinned end to end by asserting the mint step's `databaseId` equals the mailbox's `idempotencyKey`), with the instance guid as `collectionKey`, so a replayed attempt of that step is handed the mailbox the first attempt published instead of minting an orphan. Mint outcomes are modeled as `MailboxMintResult`: `Minted` (201/200, replay not distinguished) records the mailbox in the carry; `Rejected` (400 → permanent `MailboxRejected`, most often a `Timeout` past the engine's `MaxMailboxTimeout`, which app startup cannot check because the limit is the engine's); `AtCapacity` (429 → **retryable** `MailboxAtCapacity`, carrying the engine's detail so the first failure names the at-cap collection rather than a bare status). An empty `StepId` is a permanent `MailboxStepIdMissing` (an empty key is a constant, so it would collapse every mailbox in the namespace onto one shared inbox). The stage at the mint step's index no longer opening a mailbox — its declaration withdrawn since this workflow was enqueued, or the composition reshaped so the index lands elsewhere — is a permanent `MailboxDeclarationNotFound`, and a **plain not-found verdict**: an index has no old value to search for, so there is no relocation story to tell. Every other mint failure rides the step's retry ladder, which is safe because the stage after it has not run — with one known wart, recorded as a follow-up rather than fixed: a service task type missing from DI throws `ProcessException` from inside the same `try`, so a redeploy that renamed the task away retries without ever converging. `ExecuteServiceTask.Execute` has the identical shape — same throw, same outer catch — so that wart belongs to the pipeline runtime at large, not to the mint.
- **Reading it in the declaring stage.** `ExecuteServiceTask` mints nothing any more; it reads the carry. Its `Execute` is **one switch, resolved once**: the item at the index the payload carries (`Items.ElementAtOrDefault(itemIndex)`) crossed with whether the engine handed this execution a mailbox rendezvous. Each arm is a method that assumes its shape rather than re-interrogating the item — `ExecuteStage` (a `ServiceTaskStage`, no rendezvous), `ExecuteSegmentReply` (a mid-pipeline `ReplySegment` with one), `ExecuteTerminalReply` (a `PipelineConclusion.ReplyExchange` with one), `ExecuteConclusion` (a `PipelineConclusion.FinalStep` without one) — and the rendezvous is bound by the switch and handed on as a non-nullable argument, so no arm re-asks a question the switch already answered. `ExecuteSegmentReply` runs the handler exactly as `ExecuteTerminalReply` does — same rendezvous, same guards, same message — and differs only from the verdict onwards, which is why both call a shared prelude and supply the verdict handling as delegates: a terminal's answer is mapped by `MailboxRelay.Decide` and a mid-pipeline handler's by `MailboxRelay.DecideSegment`. The mismatch arms are what is left of the guards that used to read a second index, and every one of them **names the item index**: an index past the end of `Items` is `PipelineItemNotFound`; a stage handed a rendezvous is `MailboxReceiptOnStage`; a reply item handed none is `MailboxReceiptMissing`; the conclusion handed one is `MailboxReceiptOnConclusion`. The three rendezvous mismatches additionally name **both of their routes** — engine drift, and a mid-flight reshape landing some other step's index on this shape — because with one index nothing here can tell the two apart, which is why `MailboxReceiptOnStage` no longer asserts "not built by this application's pipeline expansion" outright. `PipelineItemNotFound` is one code for every shape of step, receive steps included: the index space is items, so a receive step whose handler was withdrawn misses for the same reason a stage step does, and it stays the receiving-side twin of `MailboxDeclarationNotFound` — a plain not-found verdict, since an index resolves to one item or none and there is no old value to stand anything in for. All four are permanent, for the reason every drift guard on this path is: the step's payload never changes, so a retry replays the same index against the same code — and the runtime may not fall back to a neighboring item, since a handler answering a different exchange would read this exchange's message and settle on it. Two more codes belong to the same family but arise a step later, once a verdict is being mapped rather than an item resolved, and are recorded where they occur: `MailboxIdMissingFromState` (a hop that must address a mailbox the carry does not hold) and `PipelineSegmentNotFound` (a hop that must start what the pipeline composes after the item it ran and finds nothing there — a composition that is not well-formed, since `Items` always ends with a conclusion, rather than anything a reshape produces) — both permanent, for the same reason and with the same "resume on the enqueueing code or abandon" recovery. **Exactly one refusal still runs before the service task is resolved:** a payload naming no item at all (`MissingItemIndex` → permanent `InvalidPayloadException`), which is where an old receive step's `repliesTo` lands too, that property being skipped by deserialization — old shapes are refused, never emulated. It can run out there because a payload-shape refusal needs no pipeline; every other guard now does, since telling whether an item answers messages requires the composition. They therefore sit inside the `try`, where a throwing resolution (an unregistered task type, a throwing `Define`) turns them retryable — the known wart `MintMailbox` has in identical form, recorded and accepted rather than fixed here. `ItemIndex` stays `int?` **though it is semantically required**: `CommandPayloadSerializer.Deserialize` runs in `WorkflowEngineCommandBase`, outside any handler, so a non-nullable `int` would either throw an index-less payload out as an unhandled callback exception or, worse, bind `0` and silently dispatch the pipeline's first item. **A step carries the one item it runs, and nothing else.** That is the identity doctrine in one sentence, and everything a hop needs beyond it is composition data read off the resolved pipeline: which exchange a handler answers is `ReplySegment.OpeningIndex`/`PipelineConclusion.ReplyExchange.OpeningIndex`, and what runs after any item is whatever `WorkflowCommandSet.PlanSegment` walks to from that item's index — both `Define` fixed, read at each hop rather than carried. A receive step's payload accordingly holds its handler's item index and says nothing about the exchange; a stage's holds its own index and says nothing about the receiver its completion may start. **The second half is a reshape hazard, accepted and unguarded** — written up here (`MailboxRelay.Decide`'s xmldoc points at this section). End to end: a mid-flight reshape that moves the opening stage out from under the handler still sitting at this index makes `RecordMailboxConcluded` remove an entry the blob does not have, silently; the concluded mailbox therefore stays in the published blob; the next mint for a stage at that index hits `WorkflowCallbackStateCarry.RecordMailbox`'s refusal to carry two mailboxes for one index; and `MintMailbox.Execute`'s catch turns that throw into a `Retryable` failure that never converges. It is not defended against because the old scheme misassigned under the same reshape rather than not at all — it pointed the successor's enqueue at a stale exchange instead — so what changed is which way a reshape goes wrong, not whether it does. The declaring stage's work is handed a non-nullable `ServiceTaskMailbox` (the `Id` it publishes plus the absolute `Deadline`) read from the carry; a missing entry is a permanent `MailboxIdMissingFromState` naming both of its causes — a redeploy that *added* the declaration while a workflow enqueued against the declaration-free shape was in flight (that workflow's step list holds no mint step at all), or the mint step's record not surviving into this step's state. **The declaring stage answers a widened vocabulary of its own**, `ServiceTaskOpeningStageResult` — the stage members, mapped by `MapOpeningStageResult` exactly as `MapStageResult` maps a plain stage's, plus `Conclude(ServiceTaskResult)`, for the send whose failure already settles the task *case-side* (Fiks Arkiv's recipient-not-found send is the worked example; its refused-credentials send deliberately does **not** conclude — an app-level failure is an ordinary permanent stage failure instead, leaving the mailbox open so a fix-and-resume re-runs the send and the exchange completes). A conclusion is honored from **every** mailbox-opening stage, wherever it sits, and that is what the expansion's split rule buys: a step run ends at the first opening stage (inclusive), so such a stage is always its workflow's last step and the items composed after it are work a conclusion never starts rather than steps it would have to cancel. The split is uniform because **delegate opacity leaves nothing else on offer** — the builder cannot see whether a stage's work concludes, so "honorable" could not be narrower than "composable" without a production-only failure for a composition detail unrelated to the author's delegate. `Completed()` from such a stage is accordingly always a hand-over, and `MailboxRelay.DecideStageEnd` makes it: one route, planning from the stage's index + 1 against the pipeline this execution resolved, which yields the first receiver of **the exchange the handler composed next answers** — not necessarily the one this stage opened, since on up-front sends the send that just completed opened the later exchange of the two — and the workflow carrying the items composed after it otherwise. It enqueues either way, so it refuses an empty `StepId`. A conclusion is mapped by `MailboxRelay.DecideOpeningStageConclusion`: `Success`/`FailedPermanent` conclude the whole task — **every** mailbox the carry still holds closes (close-before-downstream, all of them before the after-workflow), no receiver is enqueued, the items composed after the stage never run, and the process advances (or not) per the carried result — while a wrapped `FailedRetryable`/`Defer` concludes nothing and acts exactly as the stage vocabulary's own member. A separate root rather than a subtype: rooting it anywhere in the `ServiceTaskStageResult` chain would put either `AwaitNextReply` within a stage's reach or `Conclude` within a reply handler's.
- **The expansion changes shape for a declaring pipeline:** Main carries only the pipeline's *first segment* — the items up to and including the **first mailbox-opening stage**, or up to but excluding the first reply handler if one comes sooner — and a handler is _not_ emitted as a Main step (it runs on each receive workflow instead; emitting it here too would answer the exchange a second time, on nothing). For up-front sends that means Main ends on the *first* send and the second rides a continuation. Main's **last step is the segment's last stage** either way, and it carries nothing about what follows: **a step knows whether it is its workflow's last by asking the pipeline about item `index + 1`** — an opening stage always is; a plain stage is iff item `index + 1` is a reply handler (`WorkflowCommandSet.ItemStartsItsOwnWorkflow`, which is the *same type test* `PlanSegment`'s stop arm makes — `is IReplyHandlerItem`, the internal interface `ReplySegment` and `PipelineConclusion.ReplyExchange` both implement, so "this item is a reply handler" has one definition and the split rule and its derivation cannot answer differently; `ExecuteServiceTask`'s `MailboxReceiptMissing` arm tests the same interface, and states its own `rendezvous is null` precondition rather than relying on the arms above it, so a third kind of handler added without a dispatch arm reaches the unknown-item throw instead of being told the engine sent no rendezvous when it sent one. **The interface carries `OpeningIndex` and nothing else, and that is the load-bearing part:** the two handler delegates stay off it because their return types *are* the two verdict vocabularies, so nothing holding an `IReplyHandlerItem` can run a handler at all — dispatch still has to name the kind it is running, and one kind cannot be run as the other. It is an interface rather than a base class because a base class is not available: `ReplyExchange` is rooted in `PipelineConclusion`, which is what makes "exactly one conclusion, and it is last" structural, and a shared base would have to re-root it); a reply handler always is, being alone in its workflow; and the conclusion is last but starts nothing. Completing a last step whose next item is that exchange's handler is what enqueues **that exchange's first receiver** — one workflow whose single step is the exchange's handler, which for a single-exchange pipeline is the pipeline's conclusion and otherwise the mid-pipeline `HandleReplies` handler the segment ends on — carrying the engine's `mailbox` declaration, enqueued by the relay as a collection head that depends on the current heads — the enqueueing workflow itself, still unsettled on its last step, so a workflow that fails after creating the receiver condemns it rather than leaving it parked on the rendezvous — with a callback token minted at _that_ hop and with the state blob the stage published. Completing a last step whose next item is anything else enqueues the pipeline's next segment instead, by the same convention and with the same key. **No hop detects a mid-flight reshape, and none is meant to:** with nothing carried, there is no carried answer for the runtime's to disagree with, and that disagreement is not reconstructed anywhere. What a reshape meets instead is the fresh read, and it cuts both ways. Adding a handler after this stage simply makes the stage start that handler's receive workflow, whose exchange resolves from the carry when the reshape left the opening stage's index where the mint ran, and otherwise fails as the legible permanent `MailboxIdMissingFromState`, or, if the index lands on some other shape, as one of the dispatch mismatches the bullet above lists. **Removing one loses work silently, and that is worth stating plainly:** a plain stage that was its workflow's last step because a handler followed it finds `ItemStartsItsOwnWorkflow` false after the exchange is composed away, returns a bare success, enqueues nothing, and its workflow settles with the items after it never run — the task neither concludes nor fails. **Only a plain stage can do that:** an opening stage always routes through `DecideStageEnd`, which always plans what follows, so it either continues the pipeline or refuses legibly. Deliberately undetected, like every other reshape hazard on this path; the boundary is the reassurance, not a guard. **One shape is refused outright, and at the verdict rather than from the relay tail:** `PlanSegment` comes back with no steps at all only when `index + 1` is past the pipeline's last item, which is **not** a reshape — no reshape produces it, because `Items` always ends with a conclusion and a conclusion starts nothing, so an item whose completion reaches this hop is never the last. The guard is for a composition that is not well-formed at all. Both deciding hops answer it with a permanent `PipelineSegmentNotFound` naming the item, for two reasons: a throw would be caught into a *retryable* failure that never converges, and every attempt of that ladder re-runs the stage's work — a send this app-lib deduplicates only as far as the stage's own `StepId` reaches. What is left is the ordinary consequence every drift guard on this path leaves: the workflow is stuck until an operator resumes it on the code that enqueued it or abandons it, with the mailbox open until its own deadline and closable by hand. **One index rides the plan, and only when the plan receives:** `ServiceTaskSegmentPlan.ReceiveOpeningIndex` names the *exchange* the plan's single handler step parks on — all a plan needs beyond its steps, the handler being the step. An index rather than a mailbox id because the id lives in the carry, and the carry is read at the **deciding** hop (`MailboxRelay.TryPlanHandover`), where a missing entry can still fail the verdict legibly; `Continue` runs after the capture, so nothing there may read one. The resolved id travels on the hand-over as a `MailboxTarget` (the mailbox, plus the opening index the receiver's operation id names) — named apart from the inbound `rendezvous` the engine hands a receive workflow, since this is the outbound "park it here" — and that nullable target is the whole of what tells the enqueue a receive workflow from a continuation. **Minting the token at the enqueueing hop buys per-hop freshness for the relay's later hops, not a longer-lived receiver 1:** `GenerateToken` sets `Expires` to the _signing code's_ expiry and `GetSigningSecret` returns the first non-expired code in configuration order, so a mint seconds after the transition's enqueue picks the same code — and the receiver's state blob was signed by that code too, which `WorkflowStateSigner` rejects once it expires. The first receiver's token and its blob both die at the app code's `ExpiresAt` — the general bound on any parked workflow described under Key Design Constraints above, which nothing here checks a declaration against. The engine's `MaxMailboxTimeout` is the only ceiling a `MailboxOptions.Timeout` is actually measured against, and it is enforced by the mint (`MailboxRejected`), never at the receiver's enqueue. The enqueue runs from inside the still-unsettled last step of the workflow that asked for it, on purpose: the receiver exists before that workflow settles, so the instance's collection never reads all-settled while an exchange is open — the **frontier-never-empty** convention that everything gating on the collection (the process-next wait, `ResolveWorkflowTaskStatus`, auto-advance) relies on without knowing mailboxes exist. `Held` accordingly counts as an _active_ and _parked_ status in `WorkflowEngineService`: a Held receiver blocks the next action and reads as `Processing`, and the process-next wait releases early with the ordinary success shape exactly as it does for a deferring service task. No waiting reason is persisted — the wording is static per task and lives in the pipeline definition.
- **The carry:** the mint is keyed on the mint step's own `StepId`, which no later step can re-derive, so the mailbox travels in the signed state blob. `WorkflowCallbackState.mailboxes` is a **map keyed by the opening stage's item index as a string** (JSON object keys are strings), each entry holding an `id` and a `deadline` (`"mailboxes": { "0": { "id": "018f4e…", "deadline": "2026-08-30T12:00:00Z" } }`) — a map from day one, so sequential multi-exchange needed no blob-format migration against in-flight workflows, and `null` rather than an empty map when nothing travels, so a workflow with no exchange publishes the blob it always did. Restoring insists those keys be **canonical** renderings of an index — `"00"` is refused, never folded onto `"0"` — because two spellings of one index would collapse into one entry here and let the blob's last writer silently win over the other exchange. One test pins those literal field names, because the round-trip tests use the same serializer both ways and would agree with themselves after a wire-shape change that broke every in-flight workflow. `WorkflowCallbackStateService.RestoreState` returns the map beside the unit of work as a `WorkflowCallbackStateCarry`, the callback controller threads that object into `ProcessEngineCommandContext.StateCarry` and back into `CaptureState`, and a command that never touches it forwards it unchanged. Its API is four methods, each named for the one thing it records or reads: `RecordMailbox(stageIndex, id, deadline)` (the mint step — re-recording the *same* mailbox is a mint replay and is accepted; a *different* mailbox for the same index is unreachable by construction and throws rather than picking a winner), `FindMailbox(stageIndex)` (the declaring stage and the hops that enqueue a receiver; `Find*` rather than `TryGet*`, since `TryGet*` in .NET means `bool` + `out`), `FindAllMailboxes()` (an opening stage's conclusion, which closes every mailbox still traveling) and `RecordMailboxConcluded(stageIndex)` (the relay). Nothing in the carry assumes the map holds at most one entry, and since a pipeline may open several, nothing upstream of it does either. A deferral is stateless as ever, but a declaring stage that defers no longer re-mints on its next attempt: the mint step is already complete, and the blob a deferral echoes back still carries its entry, so the retry is handed the same address

### The reply handler and the relay saga

- **The rendezvous, and the guards that run before the handler.** On a receive workflow the handler that answers *that receiver's exchange* runs once per rendezvous — the mid-pipeline `HandleReplies` handler for an exchange the pipeline carries on past, and the conclusion only when the terminal is what answers it — and **the message and the closure arrive as delegate parameters, not as context getters** — `onMessage(context, ServiceTaskReply)` for a delivered message, `onClosed(context, MailboxClosedReason)` when the mailbox closed with the task still unconcluded. That is why `ServiceTaskContext` is a plain record again: there is no `Mailbox`/`Reply`/`ReplyClosedReason` getter that throws outside the one execution it is valid in, and so no hand-written `PrintMembers` keeping `ToString` from throwing. Which handler runs is decided by the engine's rendezvous, never inferred: exactly one of a delivery and a disposed reason is present, and a rendezvous carrying neither or both fails the step permanently (`MailboxReceiptAmbiguous`) rather than being read as a closure — an absent message *is* the instruction to conclude, so "neither" must not quietly mean closed. An empty message is a `ServiceTaskReply` with an empty `Payload`, never a null; the engine tells the two apart and the app-lib never infers one from the other. `MailboxClosedReason` says whether the mailbox closed by `Deadline` or by `Request`, for the wording only — both mean no message can arrive, and both demand the same response. The dispatch-time drift guards run before any of these — `PipelineItemNotFound` above all, described in the dispatch bullet above — and the remaining guards on this path are all permanent, splitting on reachability: a reply-answering step handed no rendezvous (`MailboxReceiptMissing`) and a concluding step handed one (`MailboxReceiptOnConclusion`) are redeploy or engine drift, decided by the dispatch switch itself and unreachable from app code, which is why they survived the compile-time move; a delivery that does not open as something this application sealed (`MailboxDeliveryEnvelopeInvalid`) is **not** — `IServiceTaskReplyForwarder` takes the mailbox id and the service task type from its caller, deliberately, so forwarding under the wrong one seals for a different mailbox or handler and fails the unwrap here. Its other routes are a forged or altered delivery and an app code that expired while an early message waited unread at its position, which needs nothing to be wrong with the message at all — hence the wording naming it.
- **The verdict vocabulary is split at compile time rather than checked at runtime:** `ConcludeOnReplies`'s `onMessage` returns `ServiceTaskExchangeResult`, the re-rooted supertype that adds `AwaitNextReply()`, while `onClosed` returns `ServiceTaskResult`, so asking for another message on a closed mailbox is unrepresentable. **A `HandleReplies` handler answers the same split one rung down:** `onMessage` returns `ServiceTaskStageExchangeResult` — the *stage* vocabulary plus `AwaitNextReply()` — and `onClosed` returns `ServiceTaskStageResult`. Four roots, then, in two parallel pairs, and the second pair exists to make one thing uncompilable: `Success(action)` and auto-advance live on `ServiceTaskResult`, which is not below the stage root, so **a handler the pipeline carries on past cannot conclude the task or move the process** — no runtime check says so, the type does. `Completed()` there is the stage vocabulary read in its plain sense: *this exchange is concluded, run the pipeline's next segment*. A `HandleReplies` `onClosed` may answer `Completed()` too, and legitimately — an exchange the task can live without ends and the pipeline carries on — or fail the task, which is the same choice a stage has. `ServiceTaskStageAwaitNextReplyResult` duplicates `ServiceTaskAwaitNextReplyResult`'s shape on purpose: the two roots are different contracts and a type has one base, the same justification the `MailboxDisposedReason`/`MailboxClosedReason` enum pair has, and invisible at use sites because app authors only ever name the factories. (A fifth root sits outside the reply pairs: `ServiceTaskOpeningStageResult`, the mailbox-opening stage's own vocabulary — the stage members duplicated once more, plus `Conclude(ServiceTaskResult)` — separate for the same one-base reason, described under Mailboxes above.) Both duplicated types carry a `<remarks>` pointing at the other, so neither side reads as an oversight. That is where the old `AwaitNextReplyOutsideAnExchange` and `MailboxExchangeAlreadyClosed` runtime failures went — deleted with the shapes that could express them, not reimplemented defensively. A singular `ConcludeOnReply` whose `onMessage` returned `ServiceTaskResult` (so `AwaitNextReply` did not compile there either) existed briefly and was **deleted before shipping**: the runtime erased the distinction anyway, the mailbox is not capacity-1 engine-side either, and "this protocol sends one answer" is an app's expectation of its counterparty, not a platform invariant. A one-answer protocol concludes on its first message, and a stray `AwaitNextReply` on one self-reports at the deadline through the handler's own `onClosed`. Reintroducing the overload later is purely additive; the reverse would have been breaking. The plural is therefore the one reply terminal, and the runtime treats every exchange uniformly. The verdicts themselves: `AwaitNextReply()` handles this message and leaves the exchange open, `Success(action?)` / `FailedPermanent` conclude it, `FailedRetryable` retries this message with the saga unstarted, and `Defer` parks the receiver against the same frozen message.
- **A result type the runtime has no move for is a permanent failure that names the type, never a throw:** all six unmappable-result sites — `MapStageResult`, `MapOpeningStageResult`, `MapServiceTaskResult` and the `default` arms of `MailboxRelay.Decide`, `DecideSegment` and `DecideOpeningStageConclusion` — return `FailedProcessEngineCommandResult.Permanent(…, "ServiceTaskResultUnknown")`, because a throw would be caught by `ExecuteServiceTask.Execute` into a *retryable* failure that can never converge on an author mistake. Those arms are reachable from app code, which is why they are not `UnreachableException`s: the result roots declare no constructor an app can call, but they are records, and C# forbids narrowing a record's synthesized copy constructor below `protected`, so chaining that still compiles. Six tests derive that way, one per mapper, and each pins convergence rather than a throw. The relay arms deliberately do **not** close the mailbox — what closes it in those switches is the app having *concluded* the exchange, and an unrecognized verdict is no conclusion; the runtime cannot tell which of the verdicts that vocabulary has (`Success`/`Completed`, `FailedPermanent`, `AwaitNextReply`) was meant, and closing picks the most destructive reading, losing the answer even after the author fixes the bug. Left open, the deadline still bounds it, an operator can close it by hand, and a resume replays the message into the corrected handler.
- **The saga lives in exactly one place, `MailboxRelay`**, never in app-author code: `Decide` maps a terminal's verdict, `DecideSegment` a mid-pipeline handler's, `DecideStageEnd` the completion of a stage that is its workflow's last step — whichever kind of stage, and whatever the pipeline composes after it — and `DecideOpeningStageConclusion` an opening stage's conclusion of the whole task; separate methods because the vocabularies are unrelated roots and a type has one base. `DecideSegment` and `DecideStageEnd` share `TryPlanHandover`: both plan from the item they ran, at decide time, and both resolve a receiving plan's mailbox from the carry there — so a hop that finds nothing to start is a legible permanent `PipelineSegmentNotFound` (a **malformed** composition, never a reshaped one — see the expansion bullet above for why no reshape can produce it) and a broken carry a legible permanent `MailboxIdMissingFromState`, never a throw from the tail. Each maps to the callback's outcome plus a `MailboxContinuation` (a four-member closed set — neither `AwaitNextMessage` nor `ContinueAfterStage` has a path to a closure, and neither `Conclude` nor `ConcludeAndContinue` has one to a successor receiver of an exchange it closes, which is how "at most one execution concludes, per exchange" is structural rather than reviewed; `Conclude` carries a *list* of mailbox ids — one from a reply handler, every carried mailbox from an opening stage's conclusion — all closed before anything downstream starts), and `Continue` performs it. **What the two decisions share, they share from one definition:** a reply handler's failure is reported as the reason code `ServiceTaskFailedException` with the same sentence a stage's or the conclusion's failure gets, and the code and the sentence live once — `ExecuteServiceTask.FailedReasonCode`/`FailedMessage`, which both `MapFailure` and the relay's four failure arms call. An operator-visible reason code with two independent literals is a drift surface: reword one and apps see two different sentences for one condition, on a code that reaches in-flight workflows. `Continue` runs from the **callback controller after the save and re-capture**, because whatever it starts must begin on the state the handler _published_ — a successor started on the incoming blob would miss its predecessor's data and their Storage-assigned ids — and because re-capturing re-signs the blob with whatever app code is current at that hop, which is the only thing that lets an exchange outlive the code that opened it. `Conclude` **closes every mailbox it names before enqueueing the after-workflow**, and `ConcludeAndContinue` its one mailbox before enqueueing the pipeline's next segment — each in one method, because the reverse order compiles and would let a message land in an exchange already concluded; a permanent failure still closes (run before the response, so a retry repeats it) but starts nothing. `ContinueAfterStage` closes nothing at all and needs no ordering of its own — whether it starts a receiver or a continuation, no exchange of the task has been answered on that hop. A reply handler's verdict closes **exactly one** mailbox: a later exchange whose stage already sent stays open and spends its own deadline, so a resume can replay the failed handler and carry the chain on. Only an opening stage's conclusion names them all — the task is over, so no exchange of its may keep accepting messages.
- **What every enqueue is keyed on, and what the successor carries.** Each step performs **at most one** idempotency-keyed enqueue — which one is decided by the verdict, and verdicts are deterministic per the handler contract — so the **bare executing `StepId`** is the whole key, identical for every relay enqueue (first receiver, successor receiver, a concluded exchange's continuation or receiver, a last stage's continuation or receiver, after-workflow), and a crashed attempt's replay deduplicates instead of forking the relay. Suffixed keys would imply several keyed enqueues per step, which never happens; under a broken (nondeterministic) handler either scheme misbehaves, so suffixes defended nothing the system defends elsewhere. **Two receiver OperationId formats coexist, and they are load-bearing rather than cosmetic** (an integration test matches the first exactly): `Mailbox receive: {taskId} · {openingIndex}` for an exchange's **first** receiver, whichever hop enqueues it, and `Mailbox receive: {taskId} · after message {position}` for a successor receiver of the *same* exchange, enqueued by `AwaitNextMessage`. The continuation is `Mailbox continue: {taskId} · after {itemIndex}`, named for the **item it follows** — the handler that concluded its exchange, or the stage that was its own workflow's last step — because with both kinds of item ending a run, an exchange's opening index would name two different continuations of one task. Nothing identifies a workflow *by* any of them — the two prefixes are `internal const`s on `ProcessNextRequestFactory` that the relay shares — but they are the only thing telling receivers apart in ops, logs and assertions. Every receiver is enqueued by one shared relay path (a head that depends on the current head — the still-unsettled step asking for it — the exchange's mailbox declaration, a token minted at that hop, the state blob that hop published), which is the **frontier-never-empty** convention in both halves: at no instant between the exchange's start and its conclusion does the collection read all-settled. **A continuation is the same convention one level up, and two kinds of hop ask for one.** When a `HandleReplies` handler ends its exchange, `ConcludeAndContinue` closes that mailbox and enqueues the one workflow the pipeline runs next; when a stage that is its workflow's last step completes, `ContinueAfterStage` enqueues the same and closes nothing. Either way the plan is the items composed after that item, walked by the shared `WorkflowCommandSet.PlanSegment` at the **deciding** hop — from the resolution that ran the item — and ended by whatever ends a run: a mailbox-opening stage, the item before a reply handler, a reply handler standing alone, or the concluding step for a `Finally`. **The one workflow is a receive workflow when the plan's only step is a reply handler** — which is all "two reply handlers composed back to back" amounts to: no empty segment and no special case, just a next segment that happens to receive. **The decide decides and the plan travels:** each deciding hop plans once and puts the outcome on the continuation as a `MailboxHandover` — the plan as made, the item it follows, and the `MailboxTarget` when the plan receives, resolved from the carry there (a missing entry is a legible permanent `MailboxIdMissingFromState`, refused before the concluded exchange is recorded so a resume replays the handler). One shape rather than a discriminated pair, because the only thing left to discriminate is a mailbox to park on, which the enqueue must read anyway. `MailboxRelayRequest` holds no carry: `Continue` runs after the capture, so nothing there may read or write one. **Nothing at the enqueue re-derives what the decide already knew:** it resolves neither the service task nor its pipeline and plans nothing — the only thing it does to the carried steps is resolve each one's options, which `ProcessStepOptionsResolver` does from the step's own identity. The relay therefore no longer leans on the `Define` determinism contract for the segment's **shape** at this hop: with one plan there is no second plan to disagree with it. What the contract still reaches here is narrower and rides the options resolution, which does resolve the pipeline per step: nondeterminism could pair the carried steps with another composition's `MaxExecutionTime`/`RetryStrategy`/`WaitBudget`, never with another step identity or shape. That is also why the enqueue has no empty-plan check of its own — `MailboxHandover` refuses an empty plan at construction, at the one place a plan becomes a hand-over, and the deciding hops refuse that case before they get there (an empty plan enqueued as a workflow would settle at once, emptying the frontier under an open mailbox). Its constructor also refuses a plan and a target that disagree on whether the workflow receives, and a receiving plan with anything other than exactly one step: the engine resolves a workflow's rendezvous at `ProcessingOrder == 0` only, so a second step would run with none — after the first had consumed the message. The collapsed hand-over can express that shape where a discriminated pair could not, which is why the guard is stated at the type rather than left to the planner's loop in another file. The "`Define` must return the same pipeline every time" `InvalidOperationException` that once guarded a re-plan went the same way. Segments are the items split at each handler **and at each mailbox-opening stage**: segment 0 rides Main, every later segment rides the workflow its predecessor's last step enqueued, and a handler shares its workflow with nothing. **That last rule is the one thing about the split that is not a choice, and both halves of it come from opposite ends:** the engine resolves a workflow's mailbox rendezvous for its first step only (`WorkflowExecutor`, `ProcessingOrder == 0`), so a step that receives must be **first**; and the app needs it **last**, because its verdict decides whether anything composed after it runs at all and a step cannot cancel later steps of its own workflow. First and last means alone — which is why `PlanSegment` makes a handler the run's only step when the walk starts on it, and otherwise ends the run before it. The reason is written where the arms are, in `PlanSegment` itself. The continuation is an ordinary head that depends on the current head — the receiver that concluded the exchange, or the workflow whose sending stage just completed; no `mailbox` declaration of its own — carrying the transition's labels, a token minted at that hop and, as its `State`, the blob that step published: the **linear state lineage**, step → continuation → its stages → the next receiver, with no second channel. Every enqueueing hop reads that blob through one accessor (`PublishedState`) which refuses a null one, so a receiver and a continuation cannot disagree about a precondition they share: a successor started on the *incoming* blob would miss the data changes it exists to build on. The dependency chain likewise runs unbroken from Main through every hop: a failed hop condemns everything after it, and one cascade resume revives the relay. The receiver's labels, operation id and callback context belong to the relay hop that enqueues it, never to the planner — which is how "a segment's last step hands over to what follows it" stays a property every hop reproduces identically. The successor also carries the transition's labels, re-derived from the committed instance: not decoration, because `ResolveWorkflowTaskStatus` reads the task it annotates from `processNextTargetTask`, and `ListCurrentTaskProcessNextWorkflows` — the hop that finds the instance's collection at all — filters on `processNextTargetId`. A successor carrying neither is invisible to that filter, so once retention purges the transition's earlier workflows the lookup finds no collection, answers `Unblocked`, and downstream work starts on top of an open exchange. `processNextSourceId` is deliberately absent: it is unrecoverable at a later hop, and no lookup a receiver answers uses it.
- **Concluding, and what the blob stops carrying.** A successful conclusion also calls `WorkflowCallbackStateCarry.RecordMailboxConcluded(openingIndex)`, so the blob it publishes drops that stage's entry; a permanent failure does not need to, because a failing callback publishes no blob for the carry to un-say anything in. **What that protects is one stage, not the whole blob:** `RecordMailbox` refuses a conflicting re-record *per index*, so the case it prevents is the next transition opening a mailbox from a stage at the *same index* and being refused over an entry days out of date — there is no "one mailbox per blob" rule left to trip over. That same refusal is the far end of the reshape hazard the dispatch bullet records: a `RecordMailboxConcluded` that silently removed nothing leaves exactly the stale entry this guard refuses, and `MintMailbox`'s catch then retries it forever. The opening index reaches `Decide` as a parameter — beside the handler's own item index the step carried, two positions with disjoint jobs: the opening index keys the carry and the wording, the handler index is what a successor receiver's step names — sourced from `PipelineConclusion.ReplyExchange.OpeningIndex` and deliberately not through `MailboxRelayRequest`, which exists only on the `Continue` path and therefore only *after* `CaptureState`: routing the carry write through there would publish a blob still carrying the concluded mailbox's entry. `MailboxRelay.Decide` refuses `AwaitNextReply` and an auto-advancing `Success` outright when the engine sent no `StepId` (`MailboxStepIdMissing`, the same guard the mint, `DecideSegment`, `DecideStageEnd` and an advancing opening-stage conclusion carry): an empty id is a constant, and engine idempotency is scoped to `(namespace, key)`, so every exchange in the application would collapse onto one successor and one after-workflow. The guard is narrow on purpose — a conclusion that starts nothing, a retryable failure and a deferral make no keyed call, and refusing those would fail a working callback over a key it never uses. **Two enums with identical members exist on purpose:** `Models.Engine.MailboxDisposedReason` is the wire shape (public only because it hangs off the already-public `AppCallbackPayload`, which MVC model-binds) and `Features.Process.MailboxClosedReason` is what app code reads; do not merge them, or the app's vocabulary becomes a wire type the drift guard owns

### Forwarding a received message

`IServiceTaskReplyForwarder` (public; `ServiceTaskReplyForwarder` behind it, registered transient — the xmldoc tells subscribers to resolve it per message from a scope) is how an external system's answer reaches the mailbox waiting for it. It takes the **mailbox id** the system echoed back, the **service task type** whose handler reads the message, the body, and the source's **own message id**; it seals the body into a `MailboxDeliveryEnvelope` and `POST`s the delivery with that message id as the engine's `idempotencyKey` — the same value the handler reads back as `ServiceTaskReply.IdempotencyKey`, so the platform's deduplication and the handler's are about one string. **There is no lookup and no round trip:** the receive workflow's shape (its handler, its step options) was declared by the app-lib at receiver-enqueue time, so a delivery is an address, a key and a body — and the service task type is _supplied by the caller_ rather than derived, because a derivation can be wrong at signing time and then sign its own mistake, producing an envelope that verifies perfectly against the wrong handler (a defect recorded against an earlier design of this feature). **The envelope's domain (`SigningPurpose.MailboxDeliveryV1`) binds the mailbox id, the service task type and the idempotency key**, each closing one move available to a holder of engine API credentials: re-delivering a captured message into another mailbox, enqueueing a receiver against _this_ mailbox that names another task's handler, and re-delivering the same envelope under a fresh key. The tag is **length-prefixed** (counting `String.Length`, the unit it is written in) so two free-form fields cannot be re-split; the state-blob domain stays **underived** so in-flight blobs survive. `ExecuteServiceTask` unwraps at the receiving end using the three values the _delivered_ callback carries — a payload that does not open is a permanent `MailboxDeliveryEnvelopeInvalid` and the handler never runs, because the bytes at that position never change. **The status mapping lives in the forwarder and nowhere else**: `202`/`200` are both success (the source redelivering, and a retry of the forwarding call itself), `404` is `Unroutable`, `409` is `Late` — _always_ too late, never too early, since deliveries precede receivers happily and the engine has no "too early" answer — `413` is `PayloadTooLarge`, `429` is `MailboxFull`, any other 4xx is `Rejected`, and anything else is `EngineUnavailable`. Only `EngineUnavailable` and `SigningUnavailable` are `IsTransient`: a mailbox's log length never goes back down, and a closed mailbox never reopens. The forwarder **never pre-checks the mailbox's status**, because the engine looks up the idempotency key before its closed check — so a message it already holds replays as `200` even after closure, and a pre-check would dead-letter a message still waiting for its receiver. **The worked example in-tree is Fiks Arkiv** (`Altinn.App.Clients.Fiks`), the feature's first consumer: `FiksArkivServiceTask` opens the mailbox from its `SendToArchive` stage and publishes its id as the outbound message's `klientKorrelasjonsId` — the one Fiks IO field a reply echoes back — and `FiksArkivSubscriber.IncomingMessageListener` reads that echo, decrypts the payloads and forwards them, doing nothing else with the message. Two shapes there are worth copying: the subscriber decides Fiks IO redelivery from `Outcome` per case rather than from `IsTransient` alone, so every verdict is stated rather than defaulted; and its reply-address round trip is pinned by taking the wire value off the _real_ outbound request and echoing that back, because a test that builds its own echo passes whichever field the send wrote it to

## Interaction with Workflow Engine Service

The engine service (a separately-deployed runtime, built from `src/Runtime/workflow-engine` in this monorepo):

- .NET service backed by PostgreSQL
- Receives `WorkflowEnqueueRequest`, stores it, executes steps sequentially
- Returns `WorkflowEnqueueResponse.Accepted` with `DatabaseId` and `Namespace` per workflow
- Calls back to the app via HTTP POST for each app command
- Sends the step database id as `stepId` in the callback payload
- Sends `Workflow.StartAt ?? Step.CreatedAt` as the stable execution reference time
- Retries failed steps with configurable backoff (default: exponential, 1s base, 5min max delay, 24h max duration)
- `Namespace` = `{org}/{app}` is the primary isolation boundary; idempotency keys are unique within a namespace
- The instance guid is both the collection key and the `processNextInstanceGuid` label — it groups every transition of an instance
- Steps execute in order; a previous step must complete before the next begins
- `Context` (`AppWorkflowContext`) is opaque to the engine; passed through to command handlers
- Commands use `CommandDefinition` with `type: "app"` and `data: AppCommandData { commandKey, payload }`

### URL Patterns (`WorkflowEngineClient`)

- Enqueue: `POST {ApiWorkflowEngineEndpoint}/{namespace}/workflows` with `Idempotency-Key` header (required) and `Collection-Key` header (optional)
- Collection detail: `GET {ApiWorkflowEngineEndpoint}/{namespace}/collections/{collectionKey}` — returns `null` on 404
- List: `GET {ApiWorkflowEngineEndpoint}/{namespace}/workflows?collectionKey=...&label=key:value&status=...&cursor=...` — paginates through `PaginatedResponse<WorkflowStatusResponse>`
- Cancel: `POST {ApiWorkflowEngineEndpoint}/{namespace}/workflows/{workflowId}/cancel`
- Resume: `POST {ApiWorkflowEngineEndpoint}/{namespace}/workflows/{workflowId}/resume?cascade={bool}`
- Abandon: `POST {ApiWorkflowEngineEndpoint}/{namespace}/workflows/{workflowId}/abandon` — writes off a failed workflow (→ `Abandoned`); 409 means the compare-and-set lost (client returns `false`)
- Deliver: `POST {ApiWorkflowEngineEndpoint}/{namespace}/mailboxes/{mailboxId}/deliveries` with `{ idempotencyKey, payload }` — 202 appended (with the assigned `idx`), 200 the key already delivered one, 404 no such mailbox, 409 closed, 413 payload over cap, 429 log over cap. Every status comes back as a `MailboxDeliveryResult` value; only a transport failure throws

## Authorization and Data Saves

All data saves during callbacks use `StorageAuthenticationMethod.ServiceOwner()`. This is a change from the old ProcessEngine, where data operations used the end user's token.

**Design**: The app (ServiceOwner) performs all data writes during process transitions. The user authorized the action (e.g., "confirm", "reject") at the ProcessNext API entry point. After that, the app executes the transition as ServiceOwner. This means:

- **policy.xml must grant ServiceOwner write rights on all tasks** — this is a prerequisite for the workflow engine
- Storage's authorization service checks the ServiceOwner identity (from the token), not the original user
- The task in Storage's XACML resource comes from `instance.Process.CurrentTask` as persisted in Storage's DB

**Implication for task-start data saves**: Between `MutateProcessState` and the `CommitProcessState` commit boundary, task-start commands create/modify data while Storage still has the OLD task as current. This works because ServiceOwner has write access on all tasks. If Storage ever starts forwarding the real userId to the authorization service (e.g., via a header), we would need to persist the process state between the two command groups instead. The factory already separates `taskEndSteps` and `taskStartSteps`, so moving the `CommitProcessState` insert point would be straightforward.
